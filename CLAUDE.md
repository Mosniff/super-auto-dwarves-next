## Project shape (the constraints that drive everything)

- **It's an event-driven web app, not a real-time game.** No render loop, no `requestAnimationFrame`, no physics, no frames. Nothing changes on screen unless the user acts. Treat it like a normal interactive web app.
- **It's an auto-battler.** All player decisions happen in the shopping/roster-building phase. Once a battle starts it takes no input and is **fully deterministic given the two rosters** (plus its stored battle seed — see "Factions, enemies and game over (Phase 13)" → Seeded battle randomness).
- **PvP is pseudo-multiplayer.** Opponents are stored roster snapshots ("images"), not live players. There is never a live connection between players. (Details below.)

## The single most important rule: separate logic from everything else

All game logic — battle system, character progression, turn resolution, rules validation — lives in **pure TypeScript modules** completely independent of React, Next.js, Prisma, and Supabase. Pure functions: plain data in, plain data out; no database, no framework, no rendering.

```typescript
// e.g. battle.ts — pure, framework-free, database-free
export function resolveAttack(
  attacker: Character,
  defender: Character,
): AttackResult {
  // ...pure computation...
}
```

**Never embed game logic inside React components, Server Actions, or database queries.** The framework layers only ever _call_ the pure logic.

Why this matters:

1. **Persistence is trivial** — game state is plain data, serializes cleanly.
2. **Clean client/server split** — the same logic can run client-side for responsiveness and server-side for authority.
3. **Deterministic, exhaustively testable battles** — a battle is a pure function of two rosters, so it's easy to unit-test.
4. **Portability** — logic isn't tied to any framework, so future change is additive, not a rewrite.

**"Pure" does not mean "client-side."** Pure describes _how_ the code is written (no side effects, no framework coupling), not _where_ it runs. A pure module is inert until imported; it runs wherever it's imported. The **authoritative** copy of any cheatable logic runs on the **server** (imported into a Server Action). Running the same logic on the client is optional and only ever for prediction/UI — never as the source of truth. See "Security / anti-cheat model" below.

## Data layer

- Persistence covers per-user rosters and characters, plus stored roster snapshots used as PvP opponents.
- **In-memory while playing:** plain data structures (`Roster`, `Character`, etc.), mutated directly as turns happen.
- **Supabase is infrastructure, not application.** It provides Postgres (+ auth/storage). **Game logic does NOT live in Supabase** — business rules live in the pure TS modules.
- **Prisma** maps between app and Postgres. Schema-first: edit `schema.prisma`, generate migrations from the diff.
- **Server-side validation of moves and battle resolution** (in Server Actions) keeps logic authoritative and prevents client tampering. See "Security / anti-cheat model" below for the full trust model.
- **Connection strings are URLs — percent-encode passwords**. A raw % (or @ # / : ? & +, spaces) in the password inside DATABASE_URL / DIRECT_URL breaks the runtime driver with a cryptic URIError: URI malformed, even though the Prisma CLI may accept the same string. Encode special characters (% → %25, @ → %40, etc.) or use an alphanumeric password. .env.example documents the required variable names; real values live only in the gitignored .env.local.
- **Supabase, Prisma, dnd-kit and cn packages are exact-pinned (no ^/~)**, because @supabase/ssr, @dnd-kit and cn are pre-1.0 and prerelease tags have previously appeared on these packages. @dnd-kit/react and @dnd-kit/dom are both direct, exact-pinned dependencies kept at the same version (dom is imported directly to remove a plugin; see "Camp: shop, roster and intents"). Their own internal @dnd-kit dependencies are pinned by package-lock.json, not by top-level entries — don't add package.json entries for packages the code doesn't import. Upgrade deliberately, one package family at a time, and never run npm audit fix (it can silently replace pinned versions).

## PvP / pseudo-multiplayer model

PvP is a defining feature but is **not** multiplayer in the networking sense — no live connection between players, and two players never need to be online simultaneously.

Because a battle takes no input once started, its outcome is a pure function of the two rosters. So an opponent is just **data**: a cloned snapshot of some player's roster at a given turn. PvP works by (1) snapshotting and storing players' rosters, and (2) selecting a stored snapshot as the adversary and running the deterministic battle against it.

This is how Super Auto Pets operates. Mechanically it's single-player against stored opponent data. It needs only ordinary DB persistence plus the pure, deterministic battle resolver — no sockets, no sessions, no real-time anything.

## Battle data architecture

This is the technical design for how a battle is computed, transmitted, replayed, and animated. It is a direct application of the standing principles above (determinism, pure logic, server authority, shared-JS). It covers the **fundamental battle system**; abilities extend it along the seams noted below without changing this structure.

For the game-facing mechanics (the turn loop, roster rules, win/draw conditions), see the "Battle system" section in `README.md`. This section is about the **data and the code architecture**, not the rules.

### Resolve once, replay many

A battle is **not** streamed or computed live as the player watches. Because a battle is fully deterministic given two rosters, the entire battle is **resolved up front** into a complete record, and the UI **plays that record back** step by step.

A resolved battle is:

```
{ initialState, events[] }
```

- `initialState` — the two rosters as they enter combat (contiguous, front-anchored).
- `events` — a flat, ordered stream of **atomic state-change events** describing everything that happened, start to finish.

The state at **any point** in the battle is **derived**, not stored: start from `initialState` and apply events in order up to that point. Do **not** store a full roster snapshot per event — that is redundant and bloated. Store `initialState` + the event stream; derive everything else by replay. (If replay ever became expensive — it won't at 7v7 scale — occasional checkpoint snapshots are the escape hatch. Not needed.)

### The three operations (keep them separate)

1. **Generating** events — the resolver decides _what happens_ (the rules). **Backend only.**
2. **Applying** an event — `applyEvent(state, event) → newState`. Pure, deterministic, no side effects, no logging. **Shared by backend and frontend.**
3. **Logging** — recording events into the stream. This is **not** a step inside `applyEvent`; it is simply the resolver pushing each event it generates into the `events` array. **Backend only** (the frontend receives a finished array — nothing to log).

**`applyEvent` is the pure, shared core.** It is imported by both sides and is identical in both:

- **Backend resolver loop:** decide an event → push it to `events` (this _is_ the "logging") → `applyEvent` to advance working state → decide the next event. Because the resolver's only way to change state is create-record-apply, **every state change is captured automatically** — there is no separate "remember to log" step, and no way to mutate state without emitting an event.
- **Frontend playback loop:** for each event (on Advance / on a timer) → `applyEvent` to advance the displayed state → dispatch the animation for that event.

The frontend therefore **does not replicate battle logic.** It never _decides_ anything — it replays a transcript of outcomes. The complex, rules-heavy part (event _generation_) lives only on the backend; the frontend shares only the trivial part (event _application_). This is what guarantees consistency with no drift: there is exactly one `applyEvent`.

**Corollary — events carry outcomes, not just deltas.** Each event should carry enough _resulting_ state that applying it needs no game knowledge, only assignment. A `DAMAGE` event carries the resulting `hp`, not just "subtract N" — so the frontend cannot compute it wrong; it just sets the stated value.

### State-change events vs. trigger points (critical distinction)

Two different concepts must not be conflated:

- **State-change events** — things that _change game state_. These are the **logged** events: the discriminated union that makes up `events[]`. They are replayed and animated. Examples (fundamental system): `ATTACK`, `DAMAGE`, `DROP`, `BATTLE_END`.
- **Trigger points** — _named moments_ in the resolver's flow where abilities may fire (e.g. `onBattleStart`, `onAttack`, `onTakeDamage`, `onDrop`, `onBattleEnd`). These are **backend-only resolver concepts**. They are **not** logged, **not** sent to the frontend, and **not** events. They are where the resolver _decides whether to generate more state-change events_.

The relationship: applying a state-change event may reach a trigger point → the resolver checks for abilities listening there → any that fire **generate further state-change events** → which may reach further trigger points. State changes are logged; trigger points are the joints between them.

**Worked example — "on battle start, gain +2 attack":**

- "Battle start" is a **trigger point** (not logged — nothing about the start itself changes roster state).
- The resolver, at that trigger point, fires the ability, which produces a **state-change event** (e.g. `STAT_CHANGE`, target id, resulting attack) — _this_ is logged, replayed, and animated.

**The abilities seam:** in the fundamental system, the resolver passes through the trigger points but **nothing is listening**, so no ability-driven events are generated. Abilities, when added, are **listeners registered at trigger points** that emit additional state-change events. This means abilities extend _what fires at trigger points_ without changing the event-log structure or `applyEvent`. Design the trigger-point set now (as resolver skeleton) even though nothing listens yet; keep the logged-event vocabulary small and outcome-based.

**Phase 12 put the first listeners in.** The resolver runs an ordered list of battle-start sub-phases (BATTLE_START_SUB_PHASES, only onBattleStartBuffs so far) between the prepare beat and the engage beat, and abilities fire there through an injected planner; camp has its own trigger points (onExperienceGain in the experience rules, onCampStart in advanceGame). See "Abilities and armour (Phase 12)". Phase 13 added a second sub-phase (onBattleStartDamage, after the buffs) and a trigger point inside the turn loop (onTurnStart, after each turn-start beat); see "Factions, enemies and game over (Phase 13)".

### Events are a discriminated union

Logged events are a TypeScript **discriminated union** keyed on a `type` field. Each type carries exactly the fields it needs; `switch (event.type)` narrows the shape. This serves both consumers: `applyEvent` switches on type to mutate correctly, and the animation dispatcher switches on type to choose the animation — both type-checked. The union of event types also _is_ the documentation of "everything that can happen in a battle."

Every logged event carries a `beatIndex: number` (see "Animation beats" below). In TypeScript this is expressed as `BattleEvent = BattleEventPayload & BeatMetadata`, where `BattleEventPayload` is the discriminated union of payloads and `BeatMetadata` supplies the beat. The resolver emits payloads; `emitEvent` stamps the beat.

The fundamental system's seven events:

- `BATTLE_START` — `{ playerFactionId, enemyFactionId }` (the factions since Phase 13, for the opening log line). Opens the battle.
- `TURN_START` — `{ turn }`. Opens a turn (numbered from 1). Its own beat.
- `ATTACK` — `{ attackerId, targetId, value }`. The lunge/bash. Per simultaneity, a turn emits **two** (both fronts) before any `DAMAGE` (declare-then-apply). `value` is the clamped damage (never negative).
- `DAMAGE` — `{ targetId, amount, resultingHp, source, sourceAbilityId? }`. The flinch / hp-drop. Carries **resulting hp** (outcome, not delta) and a **`source`** for causality. Since Phase 13, damage dealt by an ability carries the ability's id (`sourceAbilityId`), so the log uses the ability's own line and the "−N HP" floater shows; clash damage has none.
- `DROP` — `{ characterId }`. The death. Applying it removes the character from `activeCharacters` and appends to that side's `downedCharacters`; the shuffle-forward is the automatic consequence of removing from an ordered list.
- `TIMEOUT` — `{}`. Emitted only when the turn cap is hit in a genuine stalemate (both sides still have characters). Not emitted if the cap turn also produced a wipeout.
- `BATTLE_END` — `{ outcome: "playerWin" | "enemyWin" | "draw" }`. The result.

Phase 12 added four:

- `ARMOUR_DAMAGE` — `{ targetId, amount, resultingArmour, source }`. Emitted **instead of** `DAMAGE` when the target's armour is above 0 (`amount` is the armour removed; a 0-damage hit on armour still emits it). Hp is untouched, and drop detection reads only `DAMAGE`. The rule is the pure `resolveHit` (src/lib/battle/resolveHit.ts), shared by clashes and ability damage.
- `ABILITY_ACTIVATE` — `{ characterId, abilityId }`. A character's ability fires (its battle cry). Emitted even when the ability has no valid target. Since Phase 13 it also opens each turn-start ability's own beat.
- `STAT_CHANGE` — `{ targetId, stat: "armour", amount, resultingValue, source, sourceAbilityId }`. An ability's outcome event: it carries the resulting value, so `applyEvent` only assigns it. Only armour exists as a stat so far; others join the union when an ability needs them (the stat switch is never-guarded).
- `FRONTS_ENGAGE` — `{}`. The fronts engage (its own beat, after every battle-start ability and before turn 1). Emitted only when both sides still have fighters.

`ATTACK`, `BATTLE_START`, `FRONTS_ENGAGE`, `TURN_START`, `TIMEOUT`, `BATTLE_END` and `ABILITY_ACTIVATE` are state no-ops — `applyEvent` returns state unchanged for them. `DAMAGE`, `ARMOUR_DAMAGE`, `STAT_CHANGE` and `DROP` mutate state.

### Character stat ceilings

`maxHp` — every character has a `maxHp`, a hard ceiling on current `hp`. Events that would raise `hp` above `maxHp` must clamp to it, and this clamp is applied in the **resolver** when it computes an event's resulting hp — never inside `applyEvent`, which stays a pure assignment of the stated outcome. No hp-raising event exists in the fundamental system yet (damage only lowers hp), so the ceiling is currently unexercised and documented ahead of future healing/buff events. Damage's resulting hp is **not** floored at 0 — a lethal blow's negative resulting hp is load-bearing for drop detection.

### Animation beats: one event ≠ one animation

Event granularity serves the **logic**; presentation granularity serves the **frontend**. Beats bridge them: every event carries a `beatIndex: number`, and events sharing a beat are presented together as one moment.

The **resolver** assigns beats (not the frontend — grouping is explicit metadata, never inferred from event types). `resolveBattle` keeps a `currentBeat` counter and calls `startNewBeat()` at each boundary; `emitEvent` stamps the current beat onto every payload it emits.

Each beat also carries a `beatType: BeatType` — explicit metadata naming _which kind_ of beat it is, stamped by the resolver alongside `beatIndex`. The nine beat types, in battle order, and the resolver boundary that produces each:

- `BATTLE_START` — the opening "prepare" beat (beat 0, before any `startNewBeat` call): "The {player faction plural} and the {enemy faction plural} prepare for battle" (e.g. "The dwarves and the kobolds prepare for battle"). The board closes the camp roster's gaps here; nobody moves into the action zone yet.
- `ABILITY` — (Phase 12) one beat per acting character in each battle-start sub-phase (buffs, then damage since Phase 13): its `ABILITY_ACTIVATE` and the outcome events of its effects. A sub-phase whose abilities dropped anyone ends with one `DROP` beat holding all its drops.
- `ENGAGE` — (Phase 12) the `FRONTS_ENGAGE` beat, "The parties clash!", where the fronts launch into the action zone. Skipped when a side has no fighters.
- `TURN_START` — opened before each `TURN_START` event.
- `TURN_START_ABILITY` — (Phase 13) after each turn-start beat, one short beat per active character whose ability triggers onTurnStart (bench included; player front to back, then enemy front to back), holding only its `ABILITY_ACTIVATE`.
- `CLASH` — opened before the two `ATTACK`s and two `DAMAGE`s of a turn's exchange; they all share this one beat (this is what makes simultaneity legible). "Clash" names the _beat_ — do not confuse it with the `ATTACK` _event_, which is one character's individual strike.
- `DROP` — opened before the `DROP`(s), only if someone actually drops that turn (a mutual kill puts both `DROP`s in one beat).
- `TIMEOUT` — opened before a `TIMEOUT` event (if emitted).
- `BATTLE_END` — opened before the `BATTLE_END` event.

**Event types describe outcomes (what changed), never presentation context.** The same event type may appear in different beat types — `beatType`, stamped per-emission by the resolver, carries the presentational grouping, not the event type. The animation dispatcher switches on `beatType`, never on event type.

Playback steps one beat at a time, not one event. `deriveBattlePlaybackState(resolvedBattle, playbackBeat, viewingBeat)` applies every event with `beatIndex <= playbackBeat`.

`beatDurationMs(beatType)` is the first consumer of this metadata (src/lib/battle/beatDurationMs.ts; the human tunes the values; since Phase 15 each is a base value times the animation tempo, through animationTempoMs — see "Repo tidy-up and battle flare (Phase 15)"): `DROP` 1100 ms (the most choreography), `CLASH` and `ABILITY` 800 ms ("eventful"), `BATTLE_START` 800 ms (prepare: the gaps close), `ENGAGE` 900 ms (the launch), `TURN_START_ABILITY` 300 ms (Phase 13: one per actor every turn, so kept short), and every other beat type, and `undefined` (before the first beat), 400 ms ("quiet"). The same module's abilityCasterPulseKind(beatType) picks the caster pulse: "quick" on turn-start ability beats (--ability-caster-quick-duration, 0.3 s, which must not exceed that beat), otherwise "normal". **No beat may exceed the DROP duration:** the autoplay tests step their fake timers by that ceiling, and a test guards it.

- **Source attribution** — the `source` field on `DAMAGE` says _where it came from_ (which attacker, later which ability). Self-describing causality, independent of beat grouping. Beats are about **pacing**; `source` is about **causality**.

### Playback: two independent positions

Playback tracks two positions, and conflating them is a bug:

- **`playbackBeat`** — how far the battle has progressed. `advance()` moves it forward. Battle state derives from this. It never moves backward.
- **`viewingBeat`** — which beat's log text is displayed. Back/forward controls move it — though since Phase 14 no battle UI offers them (beat browsing returns with a planned full-screen info scroll), so in practice it follows `playbackBeat`. Moving it does **not** rewind battle state — the user browses the log, they do not scrub the battle.

They usually coincide (advancing snaps the view to the new beat), but the user can page back to re-read an earlier beat while the board still shows the current situation. `advance()` always continues the battle and snaps the view forward, even if the user was browsing history.

This lives in `useBattlePlayback` (React state) on top of the pure `deriveBattlePlaybackState`.

### Playback controls (all in useBattlePlayback, src/hooks/):

advance() — step forward one beat (manual). Snaps viewingBeat to the new playbackBeat.
hasBattleStarted — true once the first beat (BATTLE_START) has been applied, i.e. playbackBeat >= 0. Since Phase 12 the board's presentation comes instead from the pure battleBoardStage(events, playbackBeat) (see "Phase transitions: the game frame and the swipe"); the hook still returns hasBattleStarted.
currentBeatCharacterEffects and playbackBeat — (Phase 12) what the playback beat did to each character (beatCharacterEffects: isActing, armourGained, brokenFromArmour, since Phase 13 isDropped, and since Phase 15 hpLost — every hit's hp loss, ability or clash, which replaced Phase 13's abilityHpLost — armourLost and dealsAbilityHit), for the beat animations; derived from the playback beat, never the viewing beat.
viewPreviousBeat() / viewNextBeat() — move viewingBeat only, to re-read history; never touch playbackBeat. Bounded by canViewPrevious / canViewNext. No UI calls them since Phase 14; they are kept, with their tests and the viewPreviousBeat / viewNextBeat message keys, for the planned full-screen info scroll.
autoplaySpeed ("off" | "slow" | "fast", src/lib/battle/autoplaySpeed.ts) and setAutoplaySpeed — (Phase 14) autoplay advances one beat after autoplayBeatDelayMs(beatType, speed): fast waits the beat's beatDurationMs, slow waits SLOW_AUTOPLAY_BEAT_DURATION_MULTIPLIER (2) times it — only the pause stretches, animations keep their timings. isPlaying is autoplaySpeed !== "off" and the battle not finished; play() / pause() remain as shorthands for fast / off. The timer is a useEffect that clears on pause/unmount and stops at the final beat. Manual advance is locked for the advanced beat's duration. Opening any battle info control ("i") switches autoplay to Off (the human's call), without changing the remembered preference.
The chosen speed is remembered in browser storage (src/components/game/autoplaySpeedPreference.ts, key super-auto-dwarves:battle-autoplay-speed): a UI preference, never game state. It is read in a useLayoutEffect, and no speed shows as pressed until the screen has mounted (a useSyncExternalStore "has mounted" flag), so there is no flash of Off. At a battle's end playback stops but the chosen speed stays selected and the speed buttons stay enabled; only Advance disables.
"Playing = watching": while isPlaying, Advance is disabled; manual control resumes when the speed is Off.
viewedBeat / viewedTurn — (Phase 14) the beat the log shows and the turn in effect at it (from deriveBattlePlaybackState), for the info scroll's header.
Beat pacing is per beat type (beatDurationMs), not a fixed interval.

## Internationalization (i18n)

The app is multilingual (currently English + Japanese) via next-intl with route-segment locales (/en/..., /ja/...). The guiding principle is the same one that governs everything else: keep language out of the pure logic. Translation is a presentation concern and lives entirely in the presentation layer.

The pure layer is language-agnostic — this is load-bearing. src/lib/battle/ never produces user-facing prose. The battle log is emitted as BattleEventDescriptor values (see types.ts): structured, language-neutral descriptors carrying resolved params ({ kind: "damage", target, amount, resultingHp }), keyed on kind. The resolver and deriveBattlePlaybackState deal only in descriptors. Never put a translatable string, a locale, or a useTranslations call inside src/lib/battle/ — if you're tempted to format a sentence there, emit a descriptor instead and translate it at the edge. This is what lets battle logic stay pure, framework-free, and testable without a locale.

Translation happens at the leaf, not in between. Descriptors flow untouched through the hook (useBattlePlayback) and the intermediate components; only the leaf that actually renders text (InfoScroll) translates them. It maps each descriptor to a message key + params via the pure helper battleLogMessage (descriptor → { key, params }), then renders useTranslations("battle"). Consequences that must be preserved: the hook returns descriptors, so its tests need no i18n provider; and battleLogMessage is pure, so the descriptor→key mapping (including the battleEnd outcome→key indirection: playerWin→victory, etc.) is exhaustively unit-testable without rendering. Note the descriptor carries the raw outcome; the victory/defeat/draw key choice is battleLogMessage's job, not the descriptor's.

Why route segments, not a cookie. Locale is a route segment so the server knows it from the URL — no client round-trip, no flash, shareable/SEO-able URLs, and it's the App Router-native next-intl path. The whole app lives under src/app/[locale]/, which owns <html lang={locale}>; there is no root layout above it. Locale redirects and prefixing are handled by the middleware (see the proxy.ts note under the framework rules).

Character names are translations, keyed by template id (Phase 13 — this reverses the earlier "names are game data" rule, the human's call once kobolds needed Japanese names). The characterName namespace has an entry for every template in both locales (a parity test checks the keys against the template list), and dwarves are written in katakana in Japanese (ボリン / オグデン / ノービン); every future template needs both. Character.name stays in the save but is no longer what's displayed (revisit if renaming ever becomes a feature). The battle log stays word-free in src/lib: the client's name function is injected into buildCharacterLabelMap (Phase 14; it replaced buildNameMap) through deriveBattlePlaybackState and useBattlePlayback, so descriptors carry each character's translated name and side ({ name, side }) without the pure layer knowing any locale.

Message files. One flat file per locale (messages/en.json, messages/ja.json), namespaced common._ (UI chrome), battle._ (log lines), characterClass.\_ (class display names, keyed by class id) shopSection.\_ (shop section headings, keyed by section id) ability.\_ (Phase 12: each ability's name, summary, level texts and battle log lines, keyed by ability id; battleLogMessage returns an optional namespace: "ability" for ability lines), faction.\_ (Phase 13: each faction's name and pluralName, keyed by faction id) and characterName.\_ (Phase 13: keyed by template id). Japanese uses full-width punctuation by convention. A parity test (src/i18n/messages.test.ts) asserts both locales have identical key sets and must be kept green by adding keys to both locales — it is the guard against one locale silently drifting. When you add a user-facing string, add its key to both files and extend the parity test's expected-key list — so a block that adds a message key must list src/i18n/messages.test.ts in its scope. ICU plurals use `=1`, never `one`: Japanese has no "one" category, so `one` silently falls through to `other` there. The characterClass keys are checked against CHARACTER_CLASS_IDS itself, so adding a class without translating it in both locales fails; likewise the shopSection keys are checked against "characters" plus PLACEHOLDER_SHOP_SECTION_IDS, the faction keys against CHARACTER_FACTION_IDS and the characterName keys against the template list. Faction words never live in src/lib: descriptors and battleLogMessage carry faction ids, and the leaf (InfoScroll) translates them through the faction namespace.

Highlighted words (Phase 14). The name tags end in Name because next-intl's values and tags share one object — a tag named after its value replaced the value. The vocabulary is deliberately minimal: no ability-name tag, and not the turn counter. ## Security / anti-cheat model

**The server is always the source of truth. The client is never trusted.** Anything a player could benefit from cheating at must be computed and validated server-side, against server-held state.

**Where "server" is, concretely:** the deployed Next.js app (on Vercel) running `"use server"` code — Server Actions, server components, route handlers — which imports the pure logic and connects to Supabase. This code is never shipped to the browser; the browser only receives the client bundle and reaches the server via the (Next.js-generated) Server Action endpoints. Database credentials live only in server-side env vars. (On Vercel the server side may run as on-demand serverless functions rather than one persistent process — irrelevant to this model; it's still server-side and privileged.)

**The core rule: the client sends _intents_, never _state_ or _outcomes_.** The client says what it wants to _do_; the server decides what _happened_.

- ✅ Client: "buy shop slot 2 → roster slot 4." Server checks what's really in slot 2, whether the player can afford it, whether slot 4 is valid; runs the pure logic against its own state; persists the result.
- ✅ Client: "start the battle." Server runs the deterministic battle from authoritative rosters and _tells_ the client who won (and hands over the event stream to replay).
- ❌ Client: "my roster is now [these characters]" → server saves it. (Forgeable — a god roster.)
- ❌ Client: "I beat the PvE enemy, grant the reward" → server grants it. (Forgeable — never fought.)

**Per-phase cheat surface:**

- **Shopping phase** holds all player agency, so it's the cheatable surface. Every buy/sell/move/upgrade is an _intent_ the server validates against authoritative state. (This mirrors a conventional server-authoritative purchase endpoint.)
- **Battle phase** is inherently cheat-resistant because battles are deterministic: the server computes the canonical outcome (and the event stream) from server-authoritative rosters. The client may _replay_ the event stream for animation, but cannot change the result. Determinism (chosen for the PvP snapshot model) doubles as anti-cheat here.

**Client-side logic, if used at all, is optional prediction only** — optimistic UI, disabling unaffordable buttons — and the server always re-validates. Never let a client-side computation stand as truth.

## Persistence & save model

This defines what is persisted and how a saved game is shaped. It applies the standing rules (server authority, intents-not-outcomes, logic separated from persistence) to the concrete User and Game models. The game systems that will eventually fill these models (cards, shopping, progression, abilities) are still undefined — see "Game logic — not yet specified"; this section defines the save container, not the systems.

A Game is a save-slot of run-state. It holds the durable inputs the pure logic operates on — never derived or presentational state, and never a half-finished battle (consistent with "resolve once, replay many" and "never store per-event snapshots"). Its fields, growing over time:

playerRoster — stored as a JSON column holding the 7-slot camp roster (CampRoster, src/lib/game/campRoster.ts): an array of exactly 7 entries, each a Character (src/lib/game/character.ts) or null (an empty slot), index 0 the front, gaps allowed anywhere. Empty slots are null rather than undefined because JSON cannot represent undefined in an array. It is validated on every load by parsePersistedCampRoster (src/lib/persistence/), which rejects anything that isn't exactly 7 characters-or-nulls. Beyond the battle stats it requires a non-empty characterTemplateId, a valid tier, at least one valid class with no repeats, (since Phase 11) an experience that is an integer from 0 to 15 (isCharacterExperience — the level is always derived, never stored; Phase 11 saves were deleted by hand, with no legacy branch), (since Phase 12) an armour that is a non-negative integer (Phase 12 saves were deleted by hand too), and (since Phase 13) a known characterFactionId — no upper bound, because characters may diverge from their template (only templates are capped at 3). It deliberately does not check that the template id exists in the module: characters are self-contained. Deliberately not normalized into related character/slot tables: the roster is always loaded as a whole for its own game, so JSON avoids an ORM-to-domain mapping layer and a relational diff on every mutation (buy, move, level-up, sell), at the cost of DB-level queryability we don't need. If a future feature genuinely needs to query across rosters (e.g. global character stats), revisit then — don't pre-normalize.
characterShopSlots — the character shop's eight slots as a JSON column (added Phase 9 as shopSlots, renamed by migration drop_purchased_listings_rename_character_shop_slots, which also dropped the Phase 8 purchasedShopListingIds column): each { slotState: "locked" }, { slotState: "offering", characterTemplateId } or { slotState: "sold" }, open slots first. Validated on every load by parsePersistedCharacterShopSlots (src/lib/persistence/). See "Camp: shop, roster and intents" → "Character shop slots".
gold — the player's current gold in this game (scalar column).
day — how many camp→battle loops the player has completed (scalar column).
depth — (Phase 13) how deep the run has gone (scalar column, default 1); it goes up with day on every battle → camp transition, so it equals day for now. Shown in the header until Phase 16, which reduced the header's status to the day; depth stays in the game state and still feeds enemy generation.
enemyEncounter — (Phase 13) the enemy for the battle in progress, as one nullable JSON column: { enemyFactionId, enemyCharacters, battleSeed } (EnemyEncounter, src/lib/game/enemyEncounter.ts), all or nothing. It is **required in battlePhase and absent in campPhase**; validated on every load by parsePersistedEnemyEncounter (a known faction, 1 to 7 valid characters through the camp roster's character validator, and an unsigned 32-bit integer seed up to MAX_BATTLE_SEED).
phase — which part of the loop the player is in (see phase machine below).
revision — an optimistic-concurrency counter (default 0), incremented by every successful save (see "Revision guard" below). It is persistence bookkeeping, not a game rule, so it lives on LoadedGameRecord and SavedGame — never on GameState, and the pure logic never sees it.

Scalars are explicit columns (type-safe, matches Prisma's strengths); the roster is JSON (matches the domain type). This split is deliberate.

**Camp-roster gaps (resolved Phase 8).** README specifies that players may arrange characters with gaps in camp, and the roster is squeezed into a gapless line when a battle begins. The saved roster is therefore the 7-slot camp roster, not the battle Roster. squeezeCampRoster (src/lib/game/campRoster.ts) is the conversion seam: it keeps the non-empty slots in front-to-back order as the battle Roster's activeCharacters, with an empty downedCharacters (nothing is downed outside battle). Battle logic still only ever receives a gapless Roster. Pre-Phase-8 saves in the old Roster shape are not supported — there is deliberately no legacy branch in the parser (nothing was live; development saves were deleted by hand).

**The single trust point.** buildGameStateFromLoadedRecord (src/lib/persistence/) is the only place a stored record becomes trusted GameState: it validates the roster with parsePersistedCampRoster, the character shop with parsePersistedCharacterShopSlots and (since Phase 13) the enemy encounter with parsePersistedEnemyEncounter (each throwing on anything malformed), enforces the encounter's phase invariant (present in battlePhase, absent in campPhase — it throws otherwise), and copies the scalars. Every handler that loads a game goes through it; never build a GameState from a record by hand.

One User has at most one Game. Modeled as a separate Game table with a userId and a unique constraint — not as game-state columns on the User row. It's one-to-one today, but a separate table makes the anticipated multi-slot future ("load a game" implies slots) a one-line constraint-drop rather than a table-extraction migration. create inserts a Game (the unique constraint enforces "one game" at the DB level), load fetches it, delete removes it (freeing the user to create again).

The phase machine (newly defined). A game loops between two phases; a brand-new game starts at campPhase, day 1.

campPhase → player advances → battlePhase
battlePhase → player advances → campPhase, and day and depth increment on this transition (refused after a lost battle — see "Factions, enemies and game over (Phase 13)" → Game over)

Both transitions are driven by a single player "advance" intent — the battle does not self-advance even though the player takes no material action during it; the player dictates when the loop continues. This keeps the loop consistent with intents-not-outcomes: the player's only lever is "advance," and the server computes what advancing means from the current phase. The transition is a pure function (game state → next game state), TDD'd like the battle resolver. adventurePhase (a future step between camp and battle) is deliberately excluded for now — build the two-state machine, extend later.

Start-of-camp reset (decided 25 Oct 2026; shop re-roll added Phase 9). The battlePhase → campPhase transition in advanceGame sets gold to CAMP_STARTING_GOLD (10, src/lib/game/campState.ts) — set, not added, so unspent gold is lost — and re-rolls every open character shop slot, sold or not, keeping the open-slot count. Since Phase 12 it then fires every onCampStart ability (campStartActivations, front to back): gold becomes CAMP_STARTING_GOLD plus the sum of their goldGained. advanceGame takes the ability lookup as an optional third argument. A new game's first camp starts the same way (createNewGameState: seven empty slots, 10 gold, day 1, campPhase, and a freshly rolled character shop of 3 open and 5 locked slots). The campPhase → battlePhase transition carries roster, gold and shop through unchanged and (since Phase 13) stores the enemy encounter created for that battle; battle → camp clears it.

Stale-advance guard. Advancing is load → compute → save, so a repeated intent (double-click, second tab) could skip a phase. Two layers prevent it: buttons disable while their action is pending (PendingSubmitButton, via useFormStatus), and the advance intent carries the phase the player expects to be leaving. advanceGameAction reads it from a form field (expectedCurrentPhase), validates it with the pure isGamePhase, and advanceGameForUser silently does nothing if the saved phase differs — it resolves without error so the refresh just shows the current state. This refines the intents-not-outcomes rule: an action may accept an intent qualifier like this, validated server-side, where the worst a tampered value can do is get the request ignored or rejected. It must never accept game state (roster, gold, day, phase-to-set) or an outcome.

Revision guard (Phase 8). Every mutation is load → compute → save, so two requests racing (two tabs, a fast double action) could each pass their checks and the second save would overwrite the first. Every save is therefore conditional: GameRepository.saveGameState(gameId, nextGameState, expectedRevision) writes only if the row's revision still equals the one that was loaded, increments it on success, and resolves true (saved) or false (the game changed since it was loaded). prismaGameRepository implements this with updateMany filtered on { id, revision } plus revision: { increment: 1 }, checking count === 1 — update can't be used because it requires a unique where and throws when nothing matches. A false is a lost race, not an error: the handler resolves quietly and changes nothing, exactly like a phase mismatch. The stale-advance guard (expected phase) still stands alongside it for advance. Camp intents additionally carry the revision their screen was rendered from (expectedRevision, an intent qualifier) because a stale screen can show the right phase with the wrong slots; a mismatch with the loaded revision is ignored the same way. loadSavedGameForUser exposes the revision on SavedGame for /play to hand to the camp.

A battle's only persistent consequence is game over (Phase 13). When the player advances out of a won or drawn battle, the roster carried forward is identical to the one that entered — everyone healed, restored, repositioned; the battle's effects existed only in the playback the player watched. Because battles are deterministic, reloading mid-battlePhase simply re-resolves the identical battle from the locked roster and the stored encounter (its seed included) — there is no battle state to lose. (The roster is locked because camp intents arriving outside campPhase are ignored as stale.) A lost battle (enemyWin) ends the run instead: the save stays in battlePhase until the player's end-run intent deletes it (see "Factions, enemies and game over (Phase 13)" → Game over). Win rewards remain a future seam on the battlePhase → campPhase transition; do not build for them speculatively.

Auth is Supabase Auth (managed), anonymous-first. Players get a silent guest session — no sign-up screen, no email, no OAuth. A guest is a real auth.users row (is_anonymous = true) with a normal uuid, so the User/Game model is identical for guests and future permanent accounts. Permanent logins (Google OAuth, email) are a deliberate later addition, added as an upgrade path by linking an identity to the existing guest — the uuid stays the same, so the player's Game comes with them. Email-based auth is deferred partly because Supabase's built-in email sender only reaches project team members and is heavily rate-limited; custom SMTP is required before any email flow can serve real players.

Where a guest is created. Only on an explicit player intent: the home page's Play button submits startPlayingAction (src/app/[locale]/startPlayingAction.ts), which runs startPlayerSession (src/lib/session/) with the real Supabase readCurrentUserId and signInAsGuest (src/lib/supabase/) and prismaUserRepository. The proxy never creates sessions — it only refreshes existing ones — because every request, including crawlers, passes through it. Do not add signInAnonymously to the proxy, a Server Component, or a page load.

Verifying identity. Server code verifies the session with supabase.auth.getClaims(), never getSession() (which trusts the cookie unverified). readCurrentUserId returns null only for a genuinely absent session and throws on any other error: treating an Auth hiccup as "signed out" would sign a returning player in as a brand-new guest and orphan their save.

Pre-launch work: the anonymous sign-in rate limit was reviewed (Supabase's default, 30 per hour per IP) and a Turnstile CAPTCHA added in Phase 14 (see "Deployment and hosting (Phase 14)"). Still deliberately not built: a periodic cleanup of abandoned anonymous users (the delete trigger already cascades to Game); and a "save your progress" prompt, since a guest who clears their cookies loses access to their save.

Save flow and screens. The home menu and the saves page live in the (menu) route group, whose shared layout owns the title so it never moves between them; each page's card slides in via MenuCardTransition (enter-only, honours reduced motion). Play → startPlayingAction (guest session) → /saves, which shows one SaveSlab: empty with "New game" (createGameAction), or filled with started date (formatted in UTC deliberately, to avoid server/browser hydration mismatches), day, phase, Resume (/play) and Delete (confirmed via AlertDialog, deleteGameAction). A duplicate create (double-submit or second tab) is treated as success and goes to the existing save. /play loads the save via loadSavedGameForUser and renders its screen inside the persistent GameScreen frame (see "Phase transitions: the game frame and the swipe"). In campPhase it renders CampScreen (passing the camp roster, gold, day, the character shop slots, the character templates from listCharacterTemplates(), the revision, and the advance, buy and reposition actions). In battlePhase it resolves the battle on the server — resolveCampBattle(playerCampRoster, enemyEncounter) (src/lib/game/) squeezes the saved camp roster and runs resolveBattle against the stored encounter, with both factions and a fresh seeded random source from its battleSeed — and renders BattleScreen (with the resolved battle and the saved camp roster, which it shows as-is before the first beat), which only plays back the { initialState, events } it is given and never computes an outcome. No session → /, no save → /saves. Pages and actions never sign anyone in. The enemy comes from the stored encounter, generated at camp → battle (see "Factions, enemies and game over (Phase 13)"). If the stored battle was lost, /play also passes the outcome down and a game-over screen for the header's Continue button. The old placeholder (DUMMY_ENEMY_ROSTER and buildPlaceholderEnemyEncounter in src/lib/game/dummyEnemyRoster.ts, a single Borin) survives only as advanceGame's fixture-convenience default for its createEnemyEncounter argument; the server always passes real generation.

Identity spans two schemas. Supabase Auth owns auth.users; Prisma owns our public."User", which mirrors the auth user's uuid. There is deliberately NO foreign key between them: Prisma does not support cross-schema foreign keys, and Supabase documents that referencing its managed schemas causes schema drift as it evolves them. The link is therefore a convention, not a constraint. Deletion is reconciled by an after delete trigger on auth.users (see prisma/manual-sql/), which removes our User row and cascades to the Game. Our User row is created by an idempotent application-side upsert (UserRepository.ensureUserExists, implemented in prismaUserRepository.ts) that runs on every start-playing, not only the first — which also self-heals a session that exists without a User row. This is deliberately NOT an AFTER INSERT trigger on auth.users: a failing trigger blocks every sign-up with Supabase's opaque "Database error saving new user", fires for every bot-created guest, and lives outside the tested codebase. Deletion stays a trigger because users can be deleted outside the app (dashboard, GDPR tooling); creation can only happen through our own code. Do not add a cross-schema foreign key, and do not list auth in the datasource's schemas property.

Mutations follow the existing intents-not-outcomes rule (see "Security / anti-cheat model"): there is never an endpoint that accepts a client-supplied roster or game state. The client sends intents ("advance", "buy character shop slot N into roster slot M", "move slot A to slot B", "merge slot A into slot B", "sell slot N", "end the run"); the server reads the authoritative Game, validates, runs pure logic, and persists the result. The JSON storage format does not weaken this — cheating is prevented at the API boundary, independent of how the roster is stored.

## Camp: shop, roster and intents

Phase 8 part one made the camp playable — buying dwarves into a 7-slot roster and arranging them, by click or by drag, all server-authoritative — and Phase 9 part 4 replaced its placeholder shop with the real character shop. The game rules it implements are listed under "Game logic — not yet specified" → Defined.

**Pure rules (src/lib/game/).** campRoster.ts (CampRoster, CAMP_ROSTER_SLOT_COUNT, createEmptyCampRoster, isCampRosterSlotIndex, squeezeCampRoster), campState.ts (CampState { campRoster, gold, characterShopSlots } — the slice of run-state the camp rules operate on — and CAMP_STARTING_GOLD), shop.ts (SHOP_CHARACTER_PRICE). buyCharacterFromShopSlot and repositionCharacter return a typed result — { outcome: "accepted", next… } or { outcome: "rejected", rejectionReason } — and never throw for a broken rule: a rejection is an expected outcome. Their check orders are documented in the code (buy: invalidRosterSlot, invalidShopSlot, shopSlotLocked, shopSlotSold, unknownCharacterTemplate, rosterSlotOccupied (a non-matching occupant), rosterSlotAtMaxLevel (a matching level-5 occupant), notEnoughGold; reposition: invalidSlot, sameSlot, sourceSlotEmpty; merge: invalidSlot, sameSlot, sourceSlotEmpty, targetSlotEmpty, charactersDoNotMatch, targetSlotAtMaxLevel; sell: invalidSlot, slotEmpty). A bought dwarf is spawned from the offered template by spawnCharacterFromTemplate under a fresh id and its shop slot becomes sold; id generation is a side effect, so it is injected (generateCharacterId) and never happens inside a pure function. buyCharacterFromShopSlot does its shop-level checks first and its character-specific checks after, with the seam commented: a future equipment section's buy rule would share the shop-level half.

**Experience, merging and selling (Phase 11, decided 15 Nov 2026).**

- **Experience.** A Character carries `experience` (0 to 15); its level is derived, never stored. characterExperience.ts holds the pure rules: EXPERIENCE_REQUIRED_PER_LEVEL_UP = [3, 3, 4, 5] (level 1→2 takes 3 XP … 4→5 takes 5), MAX_CHARACTER_EXPERIENCE (15, derived by summing), MAX_CHARACTER_LEVEL (5), isCharacterExperience, levelFromExperience, characterLevelProgressFromExperience (levelling progress, or maxLevel), addExperience (capped; reports the XP actually gained), gainExperience (+1 attack, +1 max hp **and +1 current hp** per point actually gained) and mergeCharacterInto (the target gains the consumed character's experience + 1, keeping its own id, name and slot; throws if the templates differ — a programmer error, because callers check matching first). Since Phase 12, gainExperience is a per-point loop that fires onExperienceGain abilities, and a dwarf's level sets each ability's strength (see "Abilities and armour (Phase 12)").
- **Matching** means the same characterTemplateId, regardless of name, stats or level. A level-5 dwarf is never a merge target; merging _from_ a level-5 dwarf is allowed and the gain caps at 15 (the excess, and its stat gains, are lost).
- **Merge-buy.** Buying a matching shop character onto a roster dwarf is a merge: the hire is spawned and consumed through mergeCharacterInto (a fresh hire has 0 XP, so it gives exactly 1 XP), at the normal price, and the shop slot becomes sold. buyCharacterFromShopSlot reports `acceptanceKind: "placed" | "merged"`. rosterSlotAtMaxLevel is only ever returned for a matching occupant, so previews can read "matching" from it.
- **Roster merge** (mergeRosterCharacters.ts) merges a roster dwarf into a matching one; the source slot empties. targetSlotAtMaxLevel is likewise only returned for a match.
- **Sell** (sellCharacter.ts) empties a slot and adds CHARACTER_SELL_PRICE (1, in shop.ts — flat for now; future effects will change it, and this is the one place to edit). The last dwarf may be sold; there is no confirmation. sellCharacterRejectionReason is exported so previews ask the rule whether a slot is sellable rather than assuming "occupied means sellable".

**The shop has dedicated sections (decided 9 Nov 2026).** Characters, and later equipment and so on, each get their own slots — offering kinds are never mixed within a slot. The character section is the only one built, so its names say so (CharacterShopSlot, rollCharacterShopSlots, characterShopSlots); another section would sit alongside it with its own slots, counts, rules and buy function.

**Placeholder sections (Phase 10, decided 10 and 14 Nov 2026).** Equipment (4 slots), magic (4) and food (2) are shown alongside the character section as **"Coming soon"** — they are not part of this version of the game. They are **display-only constants** — PLACEHOLDER_SHOP_SECTION_IDS (display order), PlaceholderShopSectionId and PLACEHOLDER_SHOP_SECTION_SLOT_COUNTS in src/lib/game/placeholderShopSections.ts — not stored in the save: nothing about them changes during a run, and their slot shape will change anyway when they get rules, so storing them now would mean a migration and parsers for no behaviour (the human first chose storage, then switched once the cost was laid out). They were first shown as locked and named "locked" sections; when they became "Coming soon" they were renamed to placeholder sections so the names stay true to the concept. When a section gets rules it leaves this list and gets its own module, names (e.g. EquipmentShopSlot) and storage, like the character section. Do not introduce a generic shop-slot type.

**Character shop slots (Phase 9 parts 3–4).** characterShopSlots.ts models the character shop as exactly CHARACTER_SHOP_SLOT_COUNT (8) slots — locked, offering a template id, or sold — with open slots always first. A run starts with STARTING_OPEN_CHARACTER_SHOP_SLOT_COUNT (3) open; open slots will grow during a run (rules unspecified). The open-slot count is **derived** from the slots by countOpenCharacterShopSlots (sold slots are still open) and never stored separately, so the two can never disagree. rollCharacterShopSlots(openShopSlotCount, availableCharacterTemplates, chooseRandomIndex) fills the open slots with uniformly chosen templates (duplicates allowed) and locks the rest; it throws on programmer errors (a bad count, no templates, an out-of-range index) rather than returning a rejection.

- **Rolled once per camp, on the server, and stored.** If offerings were generated per page load, a reload would be a free reroll. createNewGameState rolls a new game's shop; advanceGame's battlePhase → campPhase transition re-rolls it. Both take CharacterShopRollingSources { availableCharacterTemplates, chooseRandomIndex } as their last argument, so they stay pure and tests are deterministic. ChooseRandomIndex lives in its own module (chooseRandomIndex.ts) because any future shop section would reuse it.
- **Randomness is injected, never called.** gameActions.ts is the single place real randomness enters, on the server only: buildServerCharacterShopRollingSources (listPlayerShopCharacterTemplates() and node's crypto.randomInt) and, since Phase 13, the enemy encounter's roster rolls and battle seed. Nothing in src/lib/ calls Math.random or crypto; in-battle randomness comes from the pure seeded source (Phase 13).
- **The shop offers only player-faction templates** (Phase 13): listPlayerShopCharacterTemplates() filters the templates to PLAYER_FACTION_ID ("dwarf"), so kobolds never appear in the shop. The client never rolls and never sends an offering — only "buy character shop slot N into roster slot M".
- **The shop stores template ids, not template copies**; display and buying look templates up in the characterTemplates list, which the server supplies (the page passes listCharacterTemplates() to the camp as a prop, and the buy action passes it to the handler). parsePersistedCharacterShopSlots checks shape and ordering but deliberately not template existence — template ids are never deleted. An offering whose template can't be found is not buyable (unknownCharacterTemplate) and renders as an unavailable slot.

**Handlers (src/lib/persistence/).** buyCharacterForUser, repositionCharacterForUser, mergeCharacterForUser and sellCharacterForUser follow advanceGameForUser's server-authority pattern with a fixed check order: load (no game → throw) → not campPhase → stale → expectedRevision differs from the loaded revision → stale → build GameState via buildGameStateFromLoadedRecord → run the pure rule (rejected → return the reason, save nothing) → save with the loaded revision (false → stale). They return accepted / rejected / stale; the stale checks deliberately come before parsing the roster.

**Server Actions.** buyCharacterAction, repositionCharacterAction, mergeCharacterAction and sellCharacterAction (src/app/[locale]/gameActions.ts) read only the intent and its qualifiers — slot indices (shopSlotIndex, targetRosterSlotIndex, fromSlotIndex, toSlotIndex, intoSlotIndex, slotIndex) and expectedRevision — through parseIntegerFormValue (src/lib/forms/), which accepts only plain integer text (Number() is too forgiving: "" → 0, "1e2" → 100). Invalid input throws. Templates and prices come from the server, never the client. Accepted, rejected and stale outcomes are all followed by the same response; player-facing rejection messages are deferred along with the rest of error UX.

**In-place actions use refresh(), never a redirect.** The camp actions end with refresh() from next/cache, which re-renders the current page in place and preserves client component state. A redirect to /play — even to the page you're on — is a navigation that remounts the camp, which replayed every roster card's entrance animation on each buy (a real bug, fixed this way). Rule: an action that keeps the player on the same route uses refresh(); an action that changes route (create, delete) redirects. Advance stays on /play, so since Phase 10 it uses refresh() too: the phase swipe depends on GameScreen persisting across a phase change, and a redirect would remount it.

**Click-select is the core interaction and the accessible path.** Click an offering character shop slot then an empty roster slot to buy; click a dwarf, then an empty slot to move it or another dwarf's swap or merge half (Phase 16, below); click the selected item again to cancel; clicking a different selectable item switches the selection. Tiles are native <button>s (a shadcn Button's text styling fights a card tile; decided by the human) with aria-label, aria-pressed (= selected) and disabled. Sold, locked and unavailable shop slots are not buttons at all. It works with mouse, touch, keyboard and screen readers.

**Split drop zones (Phase 16; replaced Phase 11's merge/sell mode).** There is no interaction mode any more: campInteractionMode.ts, useCampInteractionMode, MergeSellToggle, MergeSellModeAnnouncer, SellArea and the Shift handling are gone. While a **roster** dwarf is held (clicked or dragged), every other occupied slot shows **RosterSlotZones**: a dark wash over the card (--roster-slot-zones-mask) and two half-card buttons, each a dnd-kit droppable carrying { targetKind: "rosterSlotZone", slotIndex, zoneKind: "swap" | "merge" }.

- **Top half: swap** ("Slot N: swap position with X"; visible "Swap position", uppercase by CSS; 位置を入れ替え), which repositions onto that dwarf (a swap). **Bottom half: merge** ("Slot N: merge into X"), green and showing the XP bar (CharacterCard's exported ExperienceBarContents) when the merge would go through, greyed with "MAX" for a matching level-5 dwarf, greyed for a non-match. Empty slots stay one whole-slot move target. Shop holds keep the whole-card look (merge-buy ring and badge), never the split.
- **Rules:** presentRosterSlotZones (campSelection.ts) returns { zonesShown: false } or each half's presentation (swap eligible | ineligible; merge eligible | atMaxLevel | ineligible), each derived from what clicking it would do, through the same rule previews (atMaxLevel from the merge rule's targetSlotAtMaxLevel rejection). resolveCampClick handles zone targets through resolveRosterSlotZoneClick.
- **Always mounted, hidden when not applicable** (invisible, aria-hidden, inert, droppables disabled): a target that appears mid-drag must already be registered with dnd-kit. While a slot shows its zones its whole-slot button is disabled, draws no ring or markers and its own XP bar is hidden; with a dwarf in hand, another dwarf's whole slot does nothing (presents "ineligible").
- **No gap between the halves, and an ineligible merge half stays a droppable**, so a near-miss can never fall through to a neighbouring zone.
- A side effect: while a dwarf is click-selected the zones cover the other cards, so a drag can't start from them until the selection is cleared.
- **The money pile** (MoneyPile, camp's playerRosterLeadingControls) replaced the sell box: the sack image (/images/money_pile.webp, a transparent lossless WebP) with the gold count below it (DisplayedGold, Cinzel). While a roster dwarf is held its button ("Sell <dwarf>"; moneyPileSellLabel) is a click and drop target ({ targetKind: "moneyPile" }) that glows green and shows "SELL?" (moneyPileSellPrompt; 売却？); otherwise it is mounted but inert, aria-hidden and not a drop target, like the zones. It only ever receives drops.
- The camp is select-none, so a drag or a quick double click never selects text.

**campSelection.ts is the single source of interaction logic** (src/components/game/, pure, no React — next to battleLogMessage.ts):

- resolveCampClick(selection, target, campState, characterTemplates) → { nextCampSelection, campIntentToSubmit }. Selections are { characterShopSlot, shopSlotIndex } or { rosterSlot, slotIndex }; click targets are those plus { rosterSlotZone, slotIndex, zoneKind } and { moneyPile } (Phase 16); intents are buyCharacter { shopSlotIndex, targetRosterSlotIndex }, reposition, mergeCharacters { fromSlotIndex, intoSlotIndex } or sellCharacter { slotIndex }. (Phase 11's mode argument was removed with the mode in Phase 16.) Its code comment is the authoritative statement of the click rules. Note one deliberate asymmetry: with a shop slot selected, clicking an occupied roster slot changes nothing (it does not switch to that dwarf) — which is what let Phase 11's merge-buy rule turn a click on a matching dwarf into a buy with no change here.
- Availability (isCharacterShopSlotSelectable, isBuyTargetSlot, isRosterSlotSelectable, isRepositionTargetSlot) is derived by asking the same pure rules the server runs what would happen (a preview call to buyCharacterFromShopSlot / repositionCharacter) — never by re-implementing checks like "is the slot empty", "is the shop slot sold" or "is there enough gold". Hints therefore can't disagree with the server, and rule changes flow to the UI automatically. They are hints only; the server re-validates every intent.
- isCampClickEffective: a tile is clickable exactly when its click would do something (select, cancel, switch or submit).
- resolveCampDrop: a drop is "select the dragged item, then click the target" — resolveCampClick's intent, so drops obey exactly the click rules.
- presentCampTarget: every tile's visual hint, relative to the item in hand (the drag source during a drag, otherwise the click selection): held (it is the item in hand); eligible (placing it here would submit an intent — green ring); ineligible (the click would do nothing — dimmed); neutral (no hint: nothing in hand and nothing wrong, or a click that would switch the selection rather than place). With nothing in hand, a tile holding something you could pick up shows whether you can (an unbuyable listing — too little gold, or a full roster — is ineligible); empty slots stay neutral.

- Phase 11 added **mergeTarget** (placing here would merge — the eligible ring plus an emerald ChevronsUp badge top-left; since Phase 16 only shop holds produce it, as roster merges go through the merge half) and the sell target's eligible/ineligible (now the money pile's). Its **swapTarget** presentation was removed in Phase 16 (only the swap half swaps). isRosterSlotMatchingHeldItem says whether a slot matches a held **shop** card (merge accepted, or rejected for max level); a held roster dwarf's matches show through the merge half instead. isRosterSlotSelectable(campRoster, slotIndex) is "sellable, or has a reposition target". **No component or campSelection code compares characterTemplateId.**

**Styling comes from the presentation state, never from disabled.** disabled governs only what is clickable. This is what lets a mid-drag empty slot show "eligible" while disabled for clicks, and an empty slot with nothing in hand look plainly empty. Each tile carries data-camp-target-presentation so tests can assert the state.

**Pending lock.** Intents are submitted inside useTransition; while one is in flight every tile is disabled, and the camp container is aria-busy with a wait cursor. Tiles are deliberately not dimmed (it would flicker on fast responses). Optimistic UI was deferred in favour of this lock; if it's added later (useOptimistic), the server result must always win. Since Phase 12 the start-of-camp sequence locks the camp too (see "The start-of-camp sequence (Phase 12)" below).

**Drag-and-drop is a pointer-only convenience layered over click-select** (@dnd-kit/react + @dnd-kit/dom, both exact-pinned):

- sensors={[PointerSensor]}: the keyboard sensor is removed because it starts drags on Space/Enter, which on our native buttons already mean "click" — click-select stays the single keyboard path. The default pointer activation constraints are kept: a plain click (no 5px movement, no 200ms hold) never starts a drag; touch needs a 250ms press.
- dnd-kit's Accessibility plugin is removed (plugins filtered by identity against the imported Accessibility — never by name, which minification breaks). It unconditionally overwrites aria-pressed to mean "being dragged", destroying the selected state, and its default instructions describe a keyboard drag that doesn't exist. Two CampScreen tests guard this (a selected tile keeps aria-pressed="true"; no element has aria-roledescription="draggable").
- DragOverlay renders a floating CharacterCard copy (dropAnimation={null}, so it doesn't fly back while the refresh slides the new card in); the source tile stays put, dimmed. Since Phase 16 the copy fills dnd-kit's overlay box (data-drag-overlay-card) and is scaled down by --drag-overlay-card-scale around --dnd-transform-origin (the grab point), so it shrinks toward the cursor with a short pick-up shrink.
- **Drops follow the pointer only (Phase 16).** Every camp useDroppable passes collisionDetector={campDropCollisionDetector} (campDropCollision.ts: dnd-kit's pointerIntersection, from @dnd-kit/collision, exact-pinned). dnd-kit's default falls back to the dragged copy's full-size box when the pointer is over no target, which with the shrunken copy could land a drop on a slot the small card doesn't touch; now a drop in a gap does nothing. A new camp droppable must pass it too (CD2 lists them).
- Starting a drag clears the click selection. Disabled buttons still work as drop targets (dnd-kit detects collisions geometrically — confirmed by hand).
- dnd-kit's shipped JS lacks "use client" (dropped by its bundler), so it must only be imported from files that already carry the directive.

**Shared components stay battle-safe.** RosterSlab takes an optional slotInteraction; without it (battle) it renders exactly as before. ## Phase transitions: the game frame and the swipe

Phase 10 made phase changes read as progress. When the player advances (camp → battle, battle → camp), the screen below the header swipes horizontally, always forward (the old screen leaves to the left, the new arrives from the right). Until Phase 16 only the content swiped and the roster stayed fixed as permanent screen furniture; once the camp and battle slabs looked very different, snapping the slab while the content slid looked wrong, so the whole screen, roster slab included, now swipes (the header stays put). Saves → /play is a route change and deliberately does not swipe.

- **Advance re-renders in place.** advanceGameAction ends with refresh(), not a redirect to /play. A redirect is a navigation that remounts the page; refresh() re-renders it in place, so the page's root component persists across a phase change. Everything below depends on this.
- **GameScreen is the persistent frame** (src/components/game/GameScreen.tsx). /play returns <GameScreen phase={…}> at its root in both phases, wrapping CampScreen or BattleScreen. It holds a motion AnimatePresence (initial={false}, so a first load or reload doesn't swipe) whose single child is keyed on the displayed screen — the phase, or "gameOver" once the player has pressed Continue after a lost battle (Phase 13) — inside a one-cell grid: during a swipe the outgoing and incoming screens are both mounted, stacked in that cell. The phase is display-only — it comes from the server-rendered page and is used only as an animation key, never sent anywhere.
- **GameScreenShell performs the swipe.** Since Phase 16 its <main> is the motion element (motion.main, data-game-screen-swipe), entering from x 100% and exiting to -100%, so the roster region and the content region (data-game-screen-region="roster" / "content") travel together; before that only the content region moved and the outgoing roster was hidden. It reads useIsPresent(): while its screen is exiting, the <main> carries data-game-screen-presence="exiting" and both regions are inert, so nothing on a departing screen can be clicked or focused. The slab's stone varies only top to bottom, so two slabs edge to edge read as one surface. The drag overlay (position: fixed) sits inside a transformed ancestor either way. Reduced motion makes the change instant.
- **State stays in each screen.** Each screen draws its own roster: CampScreen keeps selection, drag and the pending lock; BattleScreen keeps playback. Two alternatives were rejected. Lifting that state up so the roster is one component instance is only needed if the roster must animate continuously across a phase change (e.g. dwarves returning to their camp slots after a battle) — revisit then. A portal into a frame-owned roster area can't render during server rendering, so the roster would pop in after hydration.
- **Only the swipe exits.** Removing the keyed child plays the exit of every motion component with an exit prop inside it, except those inside their own nested AnimatePresence, which only inherit an ancestor's exit with propagate. RosterSlot's and ActiveCard's cards are nested that way, so they don't play exits during a swipe. Adding an exit prop to a motion element outside a nested AnimatePresence anywhere in the screens will make it animate on every phase change.
- **Roster cards present at mount appear in place.** RosterSlot's AnimatePresence has initial={false}: a roster that mounts (every phase change) shows its cards without the slide-in, while cards added later — buys, moves, battle shuffles — still animate.
- **A battle opens with an empty action zone.** The board has three stages (BattleBoardStage, from the pure battleBoardStage(events, playbackBeat)). **beforeBattle** (before beat 0): the player's bench shows the saved camp roster exactly as in camp, gaps and front dwarf included; the enemy bench shows its whole lineup; both action-zone slots are empty. **preparing** (from the prepare beat until the engage beat has been applied): both benches show every active character with the gaps closed, front first, and both action zones stay empty — the battle-start ability beats play here, on bench cards. **engaged** (from the engage beat on): each front character is in the action zone and its bench holds the rest; slot 0's occupant changes on this beat, so the existing on-deck launch plays then. A battle with an empty side never engages, so it stays preparing (there's no one to send forward). A card dropped by a battle-start ability before the engage (reachable since Phase 13's Yip Strike) poofs in place instead of playing the launch or the slide: RosterSlab passes the beat's dropped character ids to its bench slots, and the pure rosterSlotExitAnimation (rosterSlotAnimation.ts) puts "dropped" ahead of the front slot's "launch" and the exit kind. The rule is the pure presentBattleBoard (src/components/game/battleBoardPresentation.ts); it never changes battle state, and nothing in src/lib/battle/ knows about it. So camp → battle shows no roster change at all, and battle → camp snaps the roster to the camp lineup at the start of the swipe (battles have no consequences yet — revisit when they do).
- **Tests.** GameScreenShell.test.tsx guards the exiting state (both regions still mounted, inert, presence "exiting") by removing a shell from an AnimatePresence in jsdom, where motion keeps it mounted while the exit runs. battleBoardPresentation.test.ts covers the three stages and battleBoardStage. Swipe appearance, stacking and timing are checked by eye.

## Character data: classes, tiers and templates

Phase 9 part one made character data real, as pure, read-only TypeScript modules in src/lib/game/. Classes and tiers are **data and display only** for now — they have no gameplay effect. Their future jobs (classes affecting shop slot counts and more; tiers gating which dwarves the shop offers) are not yet specified and must not be invented.

- **Classes** (characterClasses.ts): CHARACTER_CLASS_IDS = ["warrior", "mage", "merchant", "smith", "miner"] as const, CharacterClassId derived from it, and the isCharacterClassId guard. A string-literal union defined once as a list, never a TS enum: readable in code and in saves, the compiler rejects typos, and there are no enum runtime quirks. Ids stay English in code and saves; display names are translations in the characterClass message namespace (en Warrior / Mage / Merchant / Smith / Miner; ja 戦士 / 魔法使い / 商人 / 鍛冶屋 / 鉱夫), because class names are interface labels — unlike character names, which are game data.
- **Tiers** (characterTiers.ts): CHARACTER_TIERS = [1, 2, 3, 4, 5] as const, CharacterTier derived from it, and the isCharacterTier guard — the same pattern as classes.
- **Templates** (characterTemplates.ts): CHARACTER_TEMPLATES, a read-only record keyed by template id, plus findCharacterTemplate (an own-property lookup, so a stored id like "toString" can never resolve to a prototype member) and listCharacterTemplates. A CharacterTemplate holds characterTemplateId, name, tier, characterClassIds (1 to 3), the starting attack, maxHp and armour, a required abilityId (Phase 12) and a required characterFactionId (Phase 13); every field is readonly. Templates live in a typed module — not YAML, JSON or the database — so adding a character is still "add an entry", tsc catches typos, and server, client and tests import it with no parser or file I/O. Armour and abilities arrived in Phase 12 (see "Abilities and armour (Phase 12)").
- **Template ids** are lowercase kebab-case (borin, old-khaz). An id that has been used in saves is **never renamed or deleted** — only retired from the shop — because characters keep their characterTemplateId.
- **Data guards.** characterTemplates.test.ts checks every template: key equals id, kebab-case id, valid tier, 1–3 valid and distinct classes, a non-negative integer attack and armour, and a positive integer maxHp (abilityId needs no guard: its type is CharacterAbilityId, so tsc rejects an unknown id). They guard hand-written data, so they grow in value as templates are added.
- **The templates are the human's to design.** The module holds the human's templates: the dwarves Borin (tier 1, warrior, 4 attack, 7 maxHp, Growing Lad), Ogden (tier 1, warrior, 3 attack, 8 maxHp, Tighten Those Straps Son) and Norbin (tier 1, merchant, 1 attack, 3 maxHp, Penny Pincher), and (Phase 13) the kobolds kobold-runt (Kobold Runt, tier 1, warrior, 1 attack, 3 maxHp, Yip!) and kobold-thief (Kobold Thief, tier 1, warrior, 2 attack, 3 maxHp, Yip Strike), all with 0 armour. Agents must not add templates, abilities, enemy lists or portraits.
- **One Character type** (src/lib/game/character.ts, Phase 9 parts 2 and 6): a character is { id, characterTemplateId, characterFactionId, name, tier, characterClassIds, attack, hp, maxHp, armour, experience } (the faction since Phase 13, copied from the template on spawn), used everywhere — camp roster, shop previews, saves, battle and cards. Every character comes from a template. Phase 9 first added these fields as an OwnedCharacter extension of the battle engine's older, smaller Character; two types for one concept made cards treat tier and classes as optional, so part 6 merged them and moved Character out of src/lib/battle/ into the game module, which is its natural home: a character is a game concept that the battle engine uses, not owns. Everything is stored on the character, so it can diverge from its template (renames, gained classes, stat growth — rules unspecified); template edits never reach existing characters. spawnCharacterFromTemplate(characterTemplate, newCharacterId) (its own module) is the only way one is built from a template: hp starts at maxHp and the classes list is copied, never shared with the read-only template. Current hp outside battle is persisted — the health a character takes into its next fight — and today always equals maxHp, because battles write nothing back. The battle engine fights with attack, hp and armour, plus abilities looked up through the template; tier and classes have no battle effect yet.
- **Card display** (redesigned in Phase 10): CharacterCard borrows a trading-card frame's structure with our own look — a thick border and textured frame (--texture-card-frame), a name bar (name left, tier in Roman numerals right, tierRomanNumeral in src/components/game/characterCardDisplay.ts), the portrait, a class bar (translated classes; since Phase 13 a type label: the faction, then the classes joined by a slash — "Dwarf Warrior/Mage" / ドワーフの戦士／魔法使い — through common.characterTypeLabel and common.characterClassSeparator, also on the expanded card), and a combined stats pill (the text box was dropped from the standard card; ability texts live in the expanded card — see the next bullet): ⚔ attack | ❤ current hp on dark halves. The hp number is coloured by the pure hpDisplayTone(hp, maxHp): parchment when equal, red when below ("damaged"), green when above ("buffed" — unreachable while maxHp is a hard ceiling, kept by the human's choice for future effects). The HP bar shows only when showHpBar is set, which ActiveCard sets; the hover-reveal and the compact/full variants are gone. **The card scales as a whole:** its root is a Tailwind @container carrying no container-unit styles (an element can't measure itself), and every size inside the frame is a named cqw token in globals.css's @theme inline (--text-card-_, --spacing-card-_, --radius-card-\*, --border-width-card-frame), so one layout serves a ~100px shop tile and the 288px action card, and the human tunes it in one place. The root's rounded-md matches RosterSlot's card wrapper so corners coincide. Only the portrait image mirrors (facing scaleX wrapper); bars, pill, HP bar and the Downed overlay never do, and the overlay covers the portrait.

- **Card display, Phase 11–12 changes:** the standard card has no text box (Phase 11 hid it behind a prop; Phase 12 removed the prop again, because ability descriptions live in ExpandedCharacterCard and CharacterCard does one job). The bottom row is a flex row: an optional parchment level pill ("Lv 2" / "Lv2", so it never reads as the Roman-numeral tier) at the left and the stats pill at the right. Armour shows as a lucide Shield with the number inside, top-right of the portrait (data-character-armour, accessible name from common.armourLabel), and is not rendered at 0. showInlineExperienceBar (shop) puts segments-only XP under the portrait; showRevealWash is the hover wash. ## Abilities and armour (Phase 12)

Phase 12 (decided 16–18 Nov 2026; the rulings are in the project's phase-12 rulings doc) gave characters armour and abilities. The ability designs are the human's; agents must not add or change abilities.

**Armour.** A base stat on templates, characters and saves (non-negative integer, 0 for every current template; future equipment will add it). In battle, while a character's armour is above 0 a hit goes to armour instead of hp: if the damage is at least the armour, the armour breaks (becomes 0) and the remainder is **discarded** — hp is untouched by any hit that lands on armour. All damage is "physical" for now. resolveHit (src/lib/battle/resolveHit.ts) is the one rule and returns ARMOUR_DAMAGE or DAMAGE. Log lines: "{target}'s armour absorbs {amount} damage", or "{target}'s armour breaks!" when the resulting armour is 0 (the choice is battleLogMessage's). Armour is one field (base and in-battle current) — safe only because battles write nothing back; revisit (base vs current, like hp/maxHp) when battles gain consequences.

**Abilities as data** (src/lib/game/characterAbilities.ts). One ability per template, looked up through characterTemplateId — saves store nothing about abilities. CHARACTER_ABILITY_IDS (kebab-case), CharacterAbilityTrigger, and CharacterAbility, a discriminated union keyed on abilityId whose per-level parameters are PerLevel 5-tuples (one value per level). findCharacterAbility, and findCharacterAbilityForCharacter (characterAbilityLookup.ts) for a character. Pure rules take the lookup as an **optional last argument** so tests pass fixture abilities.

- **Growing Lad** (育ち盛り, Borin, onExperienceGain): +N extra hp per XP point at level N (1…5), on top of the base +1/+1/+1; it raises max hp and current hp.
- **Tighten Those Straps Son** (ベルトを締めろ、坊主, Ogden, onBattleStartBuffs): +1 armour to allies up to N ahead at level N (1–4); at level 5 to the whole party, including himself. "Ahead" counts toward the front in the squeezed line.
- **Penny Pincher** (倹約家, Norbin, onCampStart): +N gold at the start of each camp at level N.

**Triggers.**

- **onExperienceGain** (camp). gainExperience is a per-point loop: each point actually gained adds the base stats (BASE_STAT_GAIN_PER_EXPERIENCE_POINT = 1) and then fires the ability at the level **before** that point (XP 2 → 3 fires at level-1 strength); points lost to the 15-XP cap don't fire. Effects live in experienceGainAbilities.ts. Merge-buy and roster merge both go through it (mergeCharacterInto passes the lookup on). "Promotion" in ability texts means an XP point gained. The camp's green "+N HP" floater is derived by abilityHpGainFromRefresh (max-hp rise beyond the base gain, only when XP rose) and plays after the XP floater.
- **onBattleStartBuffs** (battle). src/lib/battle/battleStartAbilities.ts: BATTLE_START_SUB_PHASES (an ordered list; damage and summon sub-phases will follow later), PlannedAbilityEffect (statChange, or damage — used since Phase 13 by Yip Strike, through resolveHit so armour applies), and planBattleStartAbility, injected into resolveBattle as an optional argument (the factions and the seeded random source come after it since Phase 13). **Simultaneity within a sub-phase:** every actor and every target and amount come from a **snapshot** taken at the start of the sub-phase (an actor knocked to 0 earlier in the same sub-phase still fires); each acting character gets its own ABILITY beat (player front → back, then enemy front → back); resulting values are read from the **current** state, so effects stack; drops are **held** to the end of the sub-phase and happen together in one DROP beat. No valid target: the battle cry still plays, with no effect. Target lines run front to back.
- **onCampStart** (camp). campStartActivations(campRoster, findAbility?) (src/lib/game/campStartAbilities.ts) lists [{ characterId, slotIndex, abilityId, goldGained }] front to back. advanceGame's battle → camp transition adds the total to the reset gold; the client re-runs the same function only to animate it (see "The start-of-camp sequence (Phase 12)").

**The battle opening.** Prepare beat (gaps close) → each battle-start sub-phase (ability beats, then any drops) → the engage beat ("The parties clash!" / 両軍がぶつかり合う！ — the fronts launch) → turn 1. See "Battle data architecture" for the events and beats, and "Phase transitions" for the board's three stages.

**Ability descriptions.** abilityDescriptionMessages (src/components/game/, pure) maps an ability's data to message keys and ICU params in the ability namespace — name, summary and five level texts — so a description's numbers always come from the data it describes. Battle log lines are `<abilityId>.battleCry` and `<abilityId>.targetEffect`.

**Battle beat animations.** beatCharacterEffects (src/lib/battle/beatCharacterEffects.ts, pure) says what the playback beat did to each character (isActing, armourGained, brokenFromArmour; Phase 13 added abilityHpLost and isDropped; Phase 15 widened abilityHpLost to hpLost and added armourLost and dealsAbilityHit); the battle screen hands { beatKey, characterEffects, beatType } (beatType since Phase 13, for the pulse speed) to its cards. The caster gets data-ability-acting="true" (a copper glow pulse and slight lift); receivers get a shield pop and a "+1 armour" floater about 0.3 s later (cause, then effect); a breaking shield keeps showing the armour it broke from, shakes, and shows "BREAK!" (data-armour-beat="gained" | "broken" | "none"). State as data attributes, motion in globals.css keyframes, nothing under reduced motion; the same attributes work on benches and the action card. BattleBeatFloaters holds the floaters. Phase 15 added flashes, receive motion, caster hops and fitted floater timing — see "Repo tidy-up and battle flare (Phase 15)".

**Portraits** (src/lib/game/characterPortraits.ts). CHARACTER_PORTRAIT_FILE_NAMES is an explicit map from template id to a file in public/character_portraits/ (borin.png, ogden.png, norbin.png); characterPortraitSrc looks it up with Object.hasOwn. CharacterPortrait renders the image, or a fallback (data-character-portrait-fallback): a brown square (--color-portrait-brown) with a large centred "?", role="img" with the character's name, never mirrored. Adding a portrait is the human's job: add the file and its map entry.

## Factions, enemies and game over (Phase 13)

Phase 13 (decided 18–19 Nov 2026; the rulings are in the project's phase-13 rulings doc) gave the run stakes and opponents. The kobold templates, abilities, list and texts are the human's design; agents must not add or change them.

**Factions** (src/lib/game/characterFactions.ts). CHARACTER_FACTION_IDS = ["dwarf", "kobold"], CharacterFactionId, isCharacterFactionId and PLAYER_FACTION_ID ("dwarf" — the player's side is always dwarves). Every template has a faction and characters copy it (stored, validated by the save parser). Words live only in the faction message namespace (name "Dwarf" / ドワーフ, pluralName "dwarves" / ドワーフ; Kobold / kobolds, コボルド / コボルド). resolveBattle takes the two sides' factions as an optional argument ({ playerFactionId, enemyFactionId }, defaulting to dwarf/dwarf as a fixture convenience); resolveCampBattle always passes both, the enemy's from its stored encounter.

**Enemy generation** (the human's design). Generated once on the server at camp → battle, stored on the Game as the enemyEncounter, and never regenerated — a reload, the advance and the end-run all re-resolve the same battle.

- **Lists** (src/lib/game/enemyLists.ts): an EnemyList is { enemyListId, enemyFactionId, entries }, each entry { characterTemplateId, cost, position } with position unique within the list. ENEMY_LISTS holds the real lists; ENEMY_LIST_DEPTH_BREAKPOINTS is an ordered depth table ({ fromDepth, enemyListId }, from depth 1, the last entry open-ended) read by chooseEnemyListIdForDepth. Today: one list, kobolds (Kobold Runt cost 1 position 1; Kobold Thief cost 2 position 2), at every depth.
- **Points** = day × depth of the battle being entered.
- **generateEnemyCharacters(enemyList, points, findCharacterTemplate, chooseRandomIndex, findAbility?)** (pure): (1) while a slot is empty and something is affordable, buy a uniformly random affordable entry; (2) each remaining point is 1 XP for a uniformly random enemy below max level, through gainExperience (so XP abilities fire); leftovers are discarded; (3) order by position, lowest at the front, copies in purchase order; (4) an empty result gets one free copy of the cheapest entry (ties: earliest in the list), added after the XP step so it has 0 XP. Ids are enemy-1, enemy-2, … from the front.
- **generateEnemyEncounter(enteringGameState, chooseRandomIndex, battleSeed)** picks the list for the depth, computes the points and builds the encounter. advanceGameAction passes it to advanceGame as createEnemyEncounter (the type is in enemyEncounter.ts), with node's crypto.randomInt for the rolls and randomInt(MAX_BATTLE_SEED + 1) for the seed.

**Seeded battle randomness.** Battles are re-resolved on every load, advance and end-run, so in-battle randomness must replay identically. createSeededChooseRandomIndex(battleSeed) (src/lib/game/seededRandomSource.ts) is a mulberry32 source with the ChooseRandomIndex signature, pinned by its tests — changing the algorithm would change the replay of every stored battle. resolveBattle takes a ChooseRandomIndex as its last optional argument (default seed 0, a fixture convenience); resolveCampBattle creates a fresh source from the stored seed on every resolve. Tests pass scripted choosers. Never Math.random in src/lib.

**Game over** (the human's calls).

- Only enemyWin ends the run; a draw survives. storedBattleOutcome(gameState) (src/lib/game/) re-resolves the stored battle and returns its outcome (null outside battlePhase); game over is decided only from it, on the server.
- **No new saved phase.** The save stays in battlePhase until the player ends the run, so a reload replays the final battle.
- advanceGameForUser quietly ignores an advance out of a lost battle (resolves without change, like a stale phase).
- **The end-run intent** (the game-over screen's "Return to menu" / メニューへもどる): endRunAction → endRunForUser (src/lib/persistence/) re-resolves the stored battle and deletes the save only for enemyWin ("runEnded"), then redirects to /saves (a route change); anything else is "runNotLost" (refresh in place) or "noSave".
- **The UI is display-only until that intent.** After a lost battle finishes, the header's button reads "Continue" and, client-side only, switches GameScreen to the game-over screen (gameOverView.tsx: GameOverViewProvider / useGameOverView; the swipe keys on the displayed screen, so it swipes like a phase change). GameOverScreen is a standalone screen without the roster slab: "Game over" / ゲームオーバー, "Your party fell on day {day}, at depth {depth}." / {day}日目、第{depth}階層でパーティは倒れた。, and the Return to menu form.

**The kobold abilities.**

- **Yip!** (キャン！, Kobold Runt, onTurnStart): no effect — only its log line ("{character} yips!" / {character}がキャンと鳴いた！) and the caster pulse. A joke ability for the weakest enemy.
- **Yip Strike** (キャン・ストライク, Kobold Thief, onBattleStartDamage): at level N, N separate hits of 1 damage, each at a random enemy. Battle cry "{character} strikes from the shadows!"; each hit logs the ability's own targetEffect line ("{target} takes {amount} damage!"); a hit absorbed by armour keeps the generic armour line.

**New triggers.**

- **onBattleStartDamage** — the second battle-start sub-phase, after the buffs and before the engage (BATTLE_START_SUB_PHASES = ["onBattleStartBuffs", "onBattleStartDamage"]). The planner receives the battle's chooseRandomIndex in its context. Yip Strike plans every hit up front from the sub-phase **snapshot**: each picks uniformly among snapshot opponents with hp above 0, so the same enemy can be picked twice and a later hit can land on an enemy already at 0 or below (wasted — a lucky break for the player, accepted). No opponent above 0 → no hits. Drops are held to the end of the sub-phase, as before.
- **onTurnStart** — after every turn-start beat, every active character (bench included) whose ability triggers onTurnStart gets its own short TURN_START_ABILITY beat, player front to back then enemy front to back. Yip! changes no state, so this trigger has no snapshot or held drops yet; the first onTurnStart ability with an effect will need the battle-start sub-phases' treatment. Position-dependent abilities will check their own condition inside the ability rather than get their own triggers.

**Presentation.** An ability hit shows a "−N HP" floater (abilityHpLossFloater: "−{amount} HP" / "HP−{amount}", U+2212 minus) from beatCharacterEffects' abilityHpLost; clash hits show none. (Reversed in Phase 15, the human's call: the floater reads hpLost, so clash damage floats on the front cards too; the key keeps its old name.) A bench card dropped before the engage poofs in place (see "Phase transitions"). Turn-start ability beats play the quick caster pulse (data-ability-caster-pulse="quick").

**Portraits.** The kobolds have no portrait files yet and show the "?" fallback until the human adds them.

- **Card badges scale with their card.** The "i" and merge badges (and the swap badge, until Phase 16 removed it) render outside CharacterCard; each host carries data-card-badge-basis (roster / active / shop) naming its card's height, and the badge takes a clamped fraction of it (globals.css → "Card badges"). Derived sizes are declared on the badge elements themselves, because a custom property containing var() resolves where it is declared.
- **The swipe grid clips only horizontally** (overflow-x-clip, not overflow-hidden, which clipped the roster's "i" at the header; not overflow-x-hidden, which forces overflow-y to auto).
- **CharacterPortrait's facing** mirrors again (data-character-portrait-mirrored), but nothing passes it: enemy portraits have their own left-facing art. For PvP, mirroring only when no left-facing image exists may be the better rule (characterPortraitSrc would decide).
- **Battle floaters are derived, not stored.** The pure floatersForBeat(beatEffect, beatKey) (src/components/game/floatersForBeat.ts — not battleBeatFloaters.ts, which would collide with BattleBeatFloaters.tsx on a case-insensitive filesystem) lists a beat's floaters during render; they sit in an AnimatePresence, so a beat change fades the old ones out (FLOATER_EXIT_DURATION_S) rather than cutting them.

**Animation tempo.** One master speed, app-wide (the human's call; there is deliberately no master size setting). ANIMATION_TEMPO in src/lib/animationTempo.ts (1.25; AT1 pins it), with animationTempoMs and animationTempoSeconds. Every beat length, the camp-start timings, every motion-driven TS constant and every CSS duration and delay — calc(base \* var(--animation-tempo, 1)), with --animation-tempo set on <html> from the constant by the locale layout — follow it, so CSS and TS can't drift apart. Excluded on purpose: hover and focus transitions, the held ring's loop and shadcn's ui components (the merge/sell announcement delay went with the mode in Phase 16). Code states base values and wraps them; a new animation must do the same.

**What a beat does to a card.**

- **Flashes.** A beat-keyed overlay tints a card: red when a hit takes hp, steel (--color-iron-300, sharper and quicker) when it lands on armour, light blue (--color-rune-blue-200) for a buff (today armourGained). Precedence hpHit → armourHit → buff, from the pure rosterSlotEffectFlashKind. Bench cards use data-roster-slot-effect-flash, front cards data-active-card-effect-flash, sharing one set of CSS rules; a turn-start beat plays a quick variant. Keying by the beat makes back-to-back hits replay.
- **Receive motion (bench only).** A hit pops the card and lets it settle with a tremble (steel smaller); a buff swells with a small strain near the top, then releases. It runs on its own layer (data-roster-slot-receive) so it composes with the caster's motion — one element can run only one CSS animation. Consecutive receives restart by parity: data-roster-slot-receive-parity alternates between two identical keyframes, because CSS restarts an animation only when its name changes. A chipped shield gets a knock (armourStruckBeat, the "struck" ArmourBeat; bench only); a break plays the existing shield break.
- **Front cards get flashes only** — no receive motion and no knock, which would fight the clash animation (the human's call).
- **Caster motion.** abilityCasterMotionKind: an attacking caster (dealsAbilityHit) hops toward the enemy with a swell — player bench down, enemy bench up, front cards sideways toward each other — the distance a fraction of the card's height; a supporting caster keeps the upward pulse, with a swell. Direction comes from facing, exposed as data-facing; camp-start casters are support (data-ability-caster-motion).
- **Unclipping.** The card wrapper no longer clips; the slot's recess lifts its clip while a beat animation plays (data-roster-slot-beat-animating) and that slot rises to z-index 10, so pops and hops can leave the slab. Shuffles keep the clip. The slab's content areas are relative with no isolate, so the cards' z-10 isn't trapped inside the slab.
- **The clash scales with the card.** clashKeyframes(facing) (activeCardClash.ts, pure) gives the pull-back, lunge and overshoot as percentages of the front card's width — the original 180 / 60 / 8 px tuning on a 288 px card. The idle position is "0%", so motion never mixes numbers with percentage strings.

**Floaters.**

- **One style for battle and camp:** an outline round the text with the colour as the fill (-webkit-text-stroke with paint-order: stroke fill), sized at a share of the card's height, clamped (globals.css → "Phase 15 battle floaters").
- **They fit inside their beat.** battleFloaterTiming(floaterKind, beatPace) in floatersForBeat.ts: on normal beats a floater starts with the flash and rises briefly; on quick turn-start beats it starts with the quick flash and rises faster; base values times the tempo. FT3 guards that every floater ends inside its beat.
- **The downed look waits for the hit.** On a beat where a card loses hp, its downed overlay and greyed portrait reveal only after the hp floater's delay (downedRevealDelaySeconds, from the same timing, through --downed-reveal-delay on CharacterCard's root); a card loaded already downed shows at once.
- **Camp floaters are CSS-animated** (RosterSlot's CampFloater; globals.css → "Phase 15 camp floater motion"), keyed by their sequence so each event replays. With motion they could stall — the XP floater never appeared while the pointer rested on the card — because hover re-renders interrupted them; CSS animations don't care about re-renders. Timings still come from the TS constants, through CSS variables. They animate under reduced motion, as before.

**Cards and the battle screen.**

- **The level shows on every battle card**, bench and front, both sides; the XP bar stays camp-only.
- **The info scroll's opening.** Before the first beat it reads "Battle!" (battleTitle; バトル！); on the battle-start beat it shows the faction matchup — the player's faction top-left, a shield emblem with "vs" (matchupVersus; VS) centred, the enemy's faction bottom-right, sliding in, keyed by the viewed beat so a revisit replays — with no header either time (infoScrollHeader). Both use **Cinzel** (next/font/google, Latin only, --font-cinzel; Japanese falls back to a system serif). Sizes are ratios of the scroll's text size, and the entrance must end inside the battle-start beat. The battleStart log line still exists but isn't shown.
- **Faction tabs.** Each battle slab names its side's faction (its plural name) on a tab in the side's colour: the enemy's in its slab's top-right, its left edge slanting; the player's (battle only, through GameScreenShell's playerRosterFactionLabel) its mirror image in the bottom-left. RosterSlab's factionLabel renders data-roster-slab-faction-label; position, padding and clip-path are per-variant rules in globals.css → "Phase 15 slab faction tabs" — the shape is cut from the label only, so nothing else clips and its width follows the text. Thin "roof" lines in the side colours edge the enemy slab's top and, in battle, the player slab's bottom (an inset box-shadow on data-roster-slab-surface, which takes no layout space; the player's keys on main's data-game-phase). The faction ids come from the BATTLE_START event (resolvedBattleFactionIds, src/lib/battle).
- **Palette.** --color-player-side (#1f5f8b) and --color-enemy-side (#a3321f) are the side colours; the highlight variables point at them.

## Testing

Use **Vitest**. (Background: Rails fuses logic and persistence in the model layer; this stack separates them — so logic is tested in isolation, with no DB.)

- **Bulk of tests = pure-logic unit tests** over the framework-free game-logic modules (battle system, progression, turn resolution). The complex battle system should be covered exhaustively. No DB setup/teardown needed. In particular: `resolveBattle` and `applyEvent` (see "Battle data architecture") are pure and should be tested exhaustively.
- **Smaller set of integration tests** for persistence wiring (Server Actions that load → run logic → save). Either against a real test Postgres (local Docker or the Supabase CLI's local instance, reset between runs) or by mocking the Prisma client.
- Shape is the standard **testing pyramid**: many fast pure-logic tests, fewer integration tests.
- **Do NOT write tests against Supabase itself** — it's infrastructure. Test our own code.
- **Persistence handlers are tested with fake GameRepository implementations** that record calls (no database — Docker isn't available in WSL). Assert on whole mapped lists — expect(recordedCalls.map((recordedCall) => recordedCall.expectedRevision)).toEqual([5]) — never index [0] on a possibly empty list, so a red fails on value instead of throwing a TypeError.
- **Shop randomness is scripted in tests.** src/test/characterShopFixtures.ts provides fixture templates, slot builders (buildOfferingCharacterShopSlot, LOCKED_CHARACTER_SHOP_SLOT, SOLD_CHARACTER_SHOP_SLOT), a fixture shop (buildFixtureCharacterShopSlots) and buildFixtureCharacterShopRollingSources(scriptedIndexes), whose chooseRandomIndex returns the scripted indexes in order (0 once exhausted) and records every option count it was asked for. Tests never depend on the real template module's data, which the human designs — except tests that deliberately check a real template, ability or portrait, and say so.
- **Shared character builders** (src/test/characterFixtures.ts, Phase 12): buildTestCharacter(overrides) and buildTestCharacterTemplate(overrides). The defaults are deliberately boring and **never change** (id fixture-character, template fixture-dwarf, "Fixture Dwarf", tier 1, ["warrior"], attack 4, hp = maxHp 7, armour 0, experience 0; the template's abilityId is growing-lad); hp follows maxHp unless given. Tests pass every value they depend on explicitly. Adding a field to Character or CharacterTemplate means one builder change, not a fixture ripple.
- **Spreads skip TypeScript's excess-property check.** Spreading a CharacterTemplate into an expected Character silently leaked abilityId into two tests' expected values. Expected values spell out their fields (or use the builder).
- **Refactor blocks may skip a value red.** A rename or switch-over that adds no rule (Phase 9 part 4c) can't fail on value against the old code — the rewritten tests crash instead. Such blocks rewrite the tests first with no source change, stop for review of the tests as the spec, then change the code to green. New behaviour still goes red first in its own block.
- **Server Actions are not unit-tested, by design.** They are kept to parse-and-delegate; the parsing helpers and handlers they call are tested. tsc, build and the human's hands-on check cover the wiring.
- **Red first, with a deliberately wrong stub** for new modules (right name and signature, wrong behaviour), and a written prediction of which tests fail and which pass trivially. Because Vitest doesn't type-check, a reshape can lead with test edits (a genuine behavioural red against the old code) and follow with the type and implementation changes.
- **Deliberate rewrites go in the red.** When a change shifts values that existing tests pin (Phase 12's engage beat moved every later beatIndex by one), the block rewrites those tests in its red, each marked `// deliberate assertion rewrite: …` (or `deliberate input rewrite`), with the exact before → after values. An agent that finds an existing test broken any other way stops and reports — it never edits a test to pass. Measuring the ripple first (on a scratch copy) keeps these lists exact.

### Testing components under the locale tree

Any component rendered in a test that calls useTranslations (or any next-intl client hook) must render inside next-intl's provider, or it throws. Use the shared renderWithMessages helper (src/test/), which wraps the component in NextIntlClientProvider with the real en.json and locale="en" and re-exports Testing Library. Because it uses the real messages, a missing translation key fails the test — which is the intended safety.

Navigation is globally mocked in tests. Components using locale-aware navigation (@/i18n/navigation's Link, useRouter, usePathname) can't render in jsdom without a mounted Next App Router context. Rather than mount Next internals, @/i18n/navigation is globally mocked in vitest.setup.ts — navigation is a framework boundary (Next/next-intl own it), not our code to unit-test. A test that needs to assert a navigation call can import the mocked useRouter and check it. Do not remove this mock or replace it with per-test mounting of Next's router context.

Two supporting config facts, both deliberate: vitest.config.ts inlines next-intl (test.server.deps.inline) so Vitest's resolver follows Next 16's package export map for next-intl's internal next/navigation import; and shadcn Select (Radix) renders its closed trigger cleanly in jsdom, so switcher-style tests assert the closed state and do not try to open the dropdown (Radix's portal + jsdom is flaky on open).

### Testing the camp UI

Test interaction **states**, not **styles**. The logic lives in the pure campSelection.ts and is tested exhaustively there; component tests then check that the right state reaches the DOM — data-camp-target-presentation, disabled, aria-pressed, aria-busy — and that clicks submit the right intent (fake actions record Object.fromEntries(formData); clicks via @testing-library/user-event). Do not assert Tailwind class names: they're tuned by eye, so such tests break on every visual tweak without catching anything, and jsdom doesn't load the stylesheet, so computed styles can't be checked either. Real appearance would need screenshot testing in a browser, which agents must not set up. Pointer dragging is not exercised in jsdom; the click tests double as the guard that dnd-kit doesn't swallow clicks. The header's advance button is tested by rendering a screen inside a real GameScreen with the button as its header (renderWithMessages forwards Testing Library's wrapper option) and finding it via [data-phase-advance], since the screens no longer render their own advance buttons.

Phase 11 additions: rerenderCampScreen (in CampScreen.test.tsx) re-renders the same camp with the refreshed props a refresh() would deliver, which is how the roster-animation tests feed a post-intent roster at revision + 1. (The keyboard-mode and announcer tests went with the merge/sell mode in Phase 16.) Animation tests assert data-roster-slot-exit-kind and data-experience-beat, and floaters by text — never motion values.

Phase 12 additions:

- **Behind a modal, use `hidden: true`.** The info dialog is modal, so Radix hides everything else from the accessibility tree; queries for background elements need `{ hidden: true }`.
- **Prefer query\* so a missing element fails on value.** getBy\* throws, which reads as a broken test rather than a red; collect queryBy\* results into one value and assert it whole.
- **Select slots by data-roster-slot-index, never by position**: the player's roster renders in visual order (backline first).
- **Several floaters in one parent need namespaced keys** (experience-N, ability-hp-N, camp-start-gold), or React reports duplicate keys.
- **Timed sequences use fake timers** (vi.useFakeTimers, advancing with act(() => vi.advanceTimersByTime(ms)), real timers restored in a finally or afterEach) and assert a list of observations taken at each step — e.g. the start-of-camp tests observe header gold, the lock, data-ability-acting and the floater at 0, 550, 850 and 2050 ms.
- **Arrival from another phase** is tested by rendering a real GameScreen and rerendering it with the new phase, so PhaseArrivalProvider sees the change.

Phase 13 additions:

- **Battle randomness is scripted in tests.** Pass resolveBattle a scripted ChooseRandomIndex (or `() => 0`) as its last argument; resolveCampBattle tests check that the stored seed reaches the resolver. Tests that need a kobold build it with buildTestCharacter and an explicit characterTemplateId ("kobold-runt", "kobold-thief") — a deliberate use of real ability data.

- **Measure the ripple against the latest state.** A red's prediction is measured on a scratch copy with every earlier block applied — a prediction measured against an older checkout was off by one in Phase 13.

## Conventions & guardrails

- Keep game logic in pure modules. Never inline it into components, actions, or queries.
- Always use explicit, descriptive names — never terse abbreviations. Full words for all variables, including short-lived callback parameters: character not c, event not e, roster.map((character) => ...) never .map((c) => ...). This is a hard rule, no exceptions for "trivial" one-liners. Readability is favoured over brevity throughout — this is a solo, learning-oriented codebase where legibility when returning to code cold matters more than saving keystrokes.
- No game loop / `requestAnimationFrame` / frame-based animation. Animations are declarative — CSS transitions for simple changes, Framer Motion for orchestrated/sequenced motion. The frame-loop escape hatch should essentially never be opened.
- Don't add Next.js features that don't do real work. Every server-rendered page, action, or route should have a genuine product reason.
- Keep persistence behind a clear seam so its implementation can change without rippling through the app.
- Prefer Server Actions for mutations; reserve Route Handlers for cases that genuinely need an HTTP endpoint.
- Server is the source of truth: validate every player action server-side against server-held state. The client sends _intents_, never _state_ or _outcomes_. See "Security / anti-cheat model."
- Battle logic: never mutate battle state except by creating an event and applying it via the shared `applyEvent`. This keeps the event log complete automatically and keeps backend/frontend consistent. See "Battle data architecture."
- Use shadcn/ui for standard app UI (menus, buttons, dialogs); these components are copied into the codebase and owned here, so edit them freely.
- Visual/UI verification is performed by the human, never by an automated agent. Do not install or invoke browser-automation tooling (Playwright, headless Chromium, chromium-cli, screenshot utilities) to check how a page renders. Agents verify with tsc --noEmit, npm test, npm run lint and npm run build; the human reviews appearance. If a task's success criterion is visual, report that the code changes are complete and let the human check.
- Agents only edit files in the working tree and run npx tsc --noEmit, npm run test:run, npm run lint and npm run build (and npm run test:coverage when asked) (build runs prisma generate, which only writes local files), each through tee into .agent-output/ (see the reporting rule below; mkdir -p .agent-output is also allowed). Anything that touches the database, version control or dependencies is the human's: git (any command), the Prisma CLI against a database (migrate dev, migrate deploy, db push, migrate reset), the Supabase CLI, and npm install / npm audit (never npm audit fix --force). Where a task needs one of these, the instructions name it as a step for the human. Agents also never open or print .env files (.env.example, which documents names only, is the one they may edit).
- **Reporting verification output: the files are the evidence, not the report.** Run every verification command through tee into the gitignored .agent-output/ folder, overwriting the previous file: npx tsc --noEmit 2>&1 | tee .agent-output/tsc.txt, npm run test:run 2>&1 | tee .agent-output/test-run.txt, npm run build 2>&1 | tee .agent-output/build.txt (mkdir -p .agent-output first if it's missing). Lint is redirected instead, so the exit code printed is lint's: npm run lint > .agent-output/lint.txt 2>&1; echo "lint exit: $?". **Through a pipe, $? is tee's exit code**, not the command's: report a piped command's exit with ${PIPESTATUS[0]} (Phase 15: a tsc line printed tee's 0). In the report, name each command you ran and copy only the final summary lines (Test Files / Tests) exactly as printed; **do not paste the output files** — the human reads or attaches them himself (`tail -6 .agent-output/test-run.txt`). Never retype, tidy or paraphrase an output line, and never replace output with prose such as "matches the prediction exactly". This applies at every STOP, red included. Why: a past report claimed a green for code that was never written, later reports replaced output with summaries, in Phase 12 several reports had retyped timing lines, and in Phase 13 a "byte-for-byte" paste contained a line the code never had. The tee files are the evidence, and the human runs npm run test:run himself before every commit and checks Start at.
- **Animations: state in React, motion in CSS where possible.** Expose an animation's trigger as a data attribute and put the motion in globals.css (the XP reveal and the XP beat both work this way). Avoid ref-dependent imperative animation (motion's useAnimate with a selector scope): in Phase 11 its scope ref was null in the browser on a merge while every jsdom test passed, even under React.StrictMode, and the cause was never pinned down. Declarative motion components (floaters, exits) are fine.
- **Never-guards.** A switch over a union ends with a default that assigns the value to never. Assert on the **discriminant** when the value was already a single variant going into the switch (ExperienceGainAbility, a BattleBoardStage string union); assert on the **object** when a union was narrowed by control flow on a correlated field before the switch (abilityDescriptionMessages, planBattleStartAbility, campStartActivations), because TypeScript narrows the object but not a separately read discriminant there. If tsc rejects a guard, stop and report — never cast around it.
- **Injected dependencies go last and are optional,** defaulting to the real implementation: the ability lookup (gainExperience, mergeCharacterInto, advanceGame, campStartActivations, campStartActivationsToPlay, generateEnemyCharacters), the battle-start planner (resolveBattle) and shop randomness. Tests pass fixtures; production passes nothing. Where no real default can exist in pure code — anything that needs the server's randomness or the save — the default is a labelled fixture convenience and the server always passes its own: resolveBattle's factions (dwarf/dwarf) and random source (seed 0), and advanceGame's createEnemyEncounter (the one-Borin placeholder) (Phase 13).

- Migrations (the human runs them): edit schema.prisma, then npx prisma migrate dev --create-only --name <name> writes the migration SQL without applying it; review the SQL; then npx prisma migrate deploy applies exactly the reviewed file and never offers to reset. migrate dev compares against the hosted database, so any drift or reset prompt is a hard stop — answer no and investigate. A required column with no default needs an empty table; development saves are deleted first (the parsers deliberately have no legacy branches). After any schema change, stop the dev server, run npx prisma generate (and rm -rf .next if needed) and restart it: a running dev server keeps the old Prisma client and fails with "Unknown argument" (Phase 13, the depth column).
- Styling values in globals.css come in two kinds. @theme inline tokens (colours, card cqw sizes, breakpoints) generate utility classes, but their values are baked into those classes, so they can't change at runtime. Values that must switch with a breakpoint, or are read by inline styles and textures through var(), are plain :root variables (shop sizes and slot looks, textures, header divider, money pile, drop zones), and components use Tailwind's var shorthand (w-(--name)). In this Tailwind version (4.3.1) every theme variable is emitted, used or not.
- Actions that keep the player on the same route (camp intents and advance) end with refresh() from next/cache, never with a redirect to the current page. See "Camp: shop, roster and intents" and "Phase transitions: the game frame and the swipe".
- The locale middleware lives in src/proxy.ts, not middleware.ts. Next 16 deprecated the middleware.ts filename convention in favour of proxy.ts; next-intl's createMiddleware works identically under either name. Do not rename it back to middleware.ts to match older next-intl docs — the deprecation warning is Next's, and proxy.ts is the current convention. The proxy composes two steps via src/lib/proxy/createComposedProxy.ts: the Supabase session refresh (src/lib/supabase/refreshSupabaseSession.ts) runs FIRST, then next-intl's routing runs on the same request, and the refresh's cookies and cache headers are copied onto next-intl's response, which is the one returned. The order is load-bearing: the refresh rewrites the request's cookies so this request's server render sees the fresh token, and next-intl forwards the request headers as they stand when it runs. Reversing it causes double refreshes and random sign-outs. Test (h) in createComposedProxy.test.ts guards the framework behaviour this relies on — if it fails after a Next or next-intl upgrade, redesign rather than patch. The proxy must stay refresh-only: no sign-in, no redirects, no route protection.

## Known non-issues (don't chase these)

A globals.css edit sometimes doesn't show in the dev server. Turbopack's persistent dev cache served stale theme changes across restarts, so it is disabled (experimental.turbopackFileSystemCacheForDev: false in next.config.ts; the cost is a slower first compile after a restart). Separately, Tailwind with Turbopack can occasionally serve the CSS one save behind: if a new globals.css variable shows as undefined in the browser, save the file again or restart the dev server. Deleting .next should no longer be needed.

removeChild ... not a child of this node when a browser translation extension is active. Running Google Translate (or similar) on top of the app can throw this React error, most visibly around the locale switcher's dropdown. It is a dev-environment / browser-extension artifact, not a code defect: the extension mutates the DOM outside React's knowledge, so React later fails to remove a node the extension already moved. It does not reproduce in a production build with the extension off. Do not "fix" this by adding translate="no"/notranslate or contorting components — suppressing translation tooling on an intentionally multilingual app is the wrong trade. Left as-is by design.

schema "pg_pgrst_no_exposed_schemas" does not exist (SQLSTATE 3F000) in the Supabase logs. This is PostgREST log noise caused by the Data API being deliberately disabled — Supabase does not fully shut PostgREST down and points it at a placeholder schema that doesn't exist. Supabase documents it as harmless. A SQL workaround exists, but it adds another hand-applied database setting outside the repo that must be undone before re-enabling the Data API, so it is deliberately not applied.

Image with src "…" is using quality "90" which is not configured in images.qualities in Vitest output. next.config.ts already allows 90; Vitest doesn't load next.config.ts, so next/image warns whenever a test renders a real portrait. Test-environment noise — don't change the config or the image for it.

"Update available 7.10.1 -> 8.0.0-rc…" from Prisma during builds. Prisma advertises its release candidate on every generate. Ignore it: upgrades are deliberate, and 8 is not released.
